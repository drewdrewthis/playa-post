# AC review — `docs/engineering/implementation-plan.md`

> Reviewer: ac-reviewer, 2026-07-30. Scope sources (in precedence order):
> `docs/engineering/architecture-addendum.md` (normative, §21/§23/§25),
> `docs/Burner_Trust_Network_Final_Handoff.pdf` (§3 scope, §4 UX, §5 safety, §9 slice),
> `docs/product/decisions.md` (D1–D3), `docs/adr/ADR-0001…0008`.
> Audited artifact: the 61 ACs M1-AC1 … M5-AC15. Scope is the specification, not the diff.

**Verdict: NOT READY as a contract.** The AC set is well above average — M2's privacy ACs
(AC3, AC5, AC10, AC14) and M4's rollback/backup ACs (AC4, AC10) are genuinely sharp and
multi-actor. But the set is *front-loaded*: M1+M2 (the 29 ACs covering ~15 % of v1 scope) carry
48 % of the ACs, while M5 — which is where two thirds of PDF §3's included scope actually lands —
covers ~40 work items with 15 ACs. Roughly half of M5's named work items have **no AC at all**.
Against the stated goal ("v1 live and working"), there is also **no AC for production** anywhere
in the plan: M4 stops at staging and M5 never re-opens deployment.

---

## Must Fix — completeness gaps

Derived from the goal, not from the AC list. Each gap is work the implementer would otherwise
decide silently.

### G1 — Production launch has zero ACs (`partial-coverage`, top severity)

The Goal is "from an empty repository to a **live deployment**", and the plan itself states
production is gated on M5 groups D and E — yet no milestone owns production. M4 is staging-only
(`M4-AC1`…`AC10` all name staging); M5-AC15 only asserts M1–M4 still pass. Nothing asserts a
production environment exists, is reachable, is correctly configured, or that real users can be
invited into it.

Implied ACs (a new M6, or an M5 group H):
- **Prod is live and is the deployed SHA**: `curl https://<prod>/health` returns 200 with `commit` equal to the tagged release SHA. *Evidence: quoted curl beside the quoted tag SHA.*
- **Prod is a distinct isolated environment**: prod and staging use different Supabase projects, different VAPID keypairs, different secrets; a staging JWT is rejected by prod with 401. *Evidence: quoted curl of prod with a staging-issued token + the two project refs.*
- **Prod launch gate is mechanical**: the release job refuses to deploy prod unless M5's D (moderation) and E (erasure/deactivation) AC suites are green. *Evidence: quoted CI job output of a deliberately failing gate.*
- **Prod backup/restore is proven** (M4-AC10 re-run against prod, pre-launch): restore into a scratch project + smoke green. *Evidence: transcript + smoke summary.*
- **Prod rollback is proven** (M4-AC4 re-run against prod, before real users exist). *Evidence: two `/health` outputs with timestamps.*
- **First real invitation**: an operator-issued invite admits exactly one real account, and the audit entry exists. *Evidence: quoted audit row + the sign-in screenshot.*

### G2 — Security bypass matrix: B2 and B4 have no AC

ADR-0002 defines B1–B12 and makes `accepted` conditional on **all twelve** being green in CI.
Mapping the ACs: B1→M1-AC4, B3→M1-AC5, B5→M2-AC5, B6→M2-AC3, B9→M2-AC10, B10→M2-AC14,
B12→M2-AC15, B7→M5-AC2, B8→M5-AC3, B11→M5-AC4. **B2 and B4 appear in work item M1.5 but in no
AC** — the two bypass rows that guard the "Supabase REST is not an unguarded second front door"
and "no `SECURITY DEFINER` backdoor" invariants. These are exactly the rows a schedule squeeze
drops silently.

- Implied AC (B2): a request to the Supabase REST endpoint for **every** table in schema `app`, with a valid user JWT, returns 404 / `PGRST106`. Catalog-driven so a newly exposed schema fails. *Evidence: vitest output naming each table + one quoted `PGRST106` body.*
- Implied AC (B4): a catalog assertion enumerating `pg_proc` for schema `app` fails if any `SECURITY DEFINER` function is absent from the checked-in allowlist file; proven by adding one in a scratch migration. *Evidence: the failing run's message naming the function, then the passing run.*
- Implied AC (matrix is a gate): `pnpm test:security` reports 12/12 B-rows executed — a skipped or unimplemented row fails the job, so the count cannot silently drop. *Evidence: quoted runner output listing all twelve row IDs.*

### G3 — Outbox failure surface (retry, backoff, dead-letter, replay) has no AC

ADR-0006 specifies `available_at = now() + least(15 min, 5s * attempts^2)`, max 8 attempts →
`dead` + alert, and "dead events are never dropped; they are inspectable and manually replayable".
The runbook item M4.9 promises a "replay a dead event" procedure. Yet **the only outbox AC is
M2-AC8 (idempotency)**. M4-AC7 fires an alert on a *manually inserted* dead row — it never proves
a real failing consumer produces one, nor that replay works.

- Implied AC: a consumer that throws is retried with growing `available_at`; after the 8th attempt the row is `status='dead'` and no further attempt occurs. *Evidence: quoted `SELECT id, attempts, status, available_at` snapshots across the 8 attempts.*
- Implied AC: a `dead` event replayed via the runbook's documented command is delivered exactly once (a `consumer_receipts` row appears; no duplicate side effect). *Evidence: quoted receipt rows before/after + the runbook command transcript.*
- Implied AC: two drainer instances running concurrently claim disjoint event sets (`FOR UPDATE SKIP LOCKED`) — no event is processed twice. *Evidence: quoted per-instance claimed-ID lists showing an empty intersection.*

### G4 — Moderation: hide-author, report reasons, and D3/D5 copy have no AC

Addendum §16 and PDF §5 name hide-author, disconnect, block-from-report, the six-value reason
taxonomy, and the copy constraint from decision D3. §21's matrix row is literally *"Viewer-controlled
dismissal **and author hiding**"*. M2-AC11 covers dismissal only; M5-AC9 covers the operator console
only. **Hide-author has no AC anywhere** except by name inside M5-AC1's twelve-name list, which is
a name-mapping check, not an assertion (see S-M5-AC1 below).

- Implied AC: after V hides author A, every current *and future* bulletin authored by A is absent from V's board, A's other viewers are unaffected, A is not told, and A remains in V's graph (hiding ≠ disconnect ≠ block). *Evidence: two quoted board responses (before/after, incl. a bulletin created after the hide) + a quoted graph response still containing A.*
- Implied AC: the report reason enum accepts exactly the six PDF values and rejects any other with a structured error naming the field; the stored reason is never exposed on any author-reachable path. *Evidence: quoted 400 response for an out-of-enum value + quoted author-facing response.*
- Implied AC (D3/D5 copy): the report confirmation UI string contains no promised timeline, outcome, jury, or strike wording — a fitness test asserts the copy constant equals the approved string. *Evidence: quoted test assertion + screenshot of the sheet.*

### G5 — Identity/GDPR: deactivation, export, reconciliation, handle rules have no AC

PDF §3 includes "Deactivation and GDPR erasure". M5-AC4 covers **erasure only**. Group E's
E2 (deactivation), E4 (data export), E5 (auth↔app reconciliation cron), E6 (privacy notice) have
no ACs. Separately, **handle rules have no AC at any milestone** despite ADR-0008 rules and issue
#14 (citext uniqueness, charset, reserved blocklist, confusable check, immutability, tombstoning)
— and escalation 3 makes handle immutability a user-facing constraint.

- Implied AC (deactivation is reversible and total-while-off): a deactivated user disappears from every other viewer's graph, board, and search; their bulletins are not visible; reactivation restores exactly the prior state. *Evidence: quoted before/off/on responses for a third-party viewer.*
- Implied AC (deactivation ≠ erasure): after deactivation the handle is still reserved and the account's rows are intact. *Evidence: quoted `SELECT` showing rows present and `deactivated_at` set.*
- Implied AC (export): a data export returns every category of the requesting user's personal data and **no** third party's private data — in particular no trust value another user set on them, and no reporter identity. *Evidence: quoted export payload key list + a grep for a seeded third-party canary, 0 matches.*
- Implied AC (handle rules): reserved handle rejected; duplicate differing only by case rejected (citext); a confusable of an existing handle rejected; an out-of-charset handle rejected; a change attempt returns `HANDLE_IMMUTABLE`. *Evidence: five quoted error responses naming the rule.*
- Implied AC (reconciliation): an auth user with no `app.users` row (and the reverse) is detected by the cron and reported, not silently ignored. *Evidence: quoted cron output naming both orphan directions on seeded fixtures.*

### G6 — Offline: retention/`expired`, cache invalidation, batching, ordering have no AC

ADR-0005 defines a fifth outcome `expired` (30-day `clientCreatedAt` bound) and precedence rules
where blocking/erasure/revoked authorization beat stale mutations. M2-AC9 covers three outcomes
(`applied`/`replayed`/`rejected`); M5-AC5 covers `conflict`. **`expired` has no AC.** F3 (cache
invalidation on block/erasure/revoked authorization) is covered only for block (M5-AC2) and
partially for erasure (M5-AC4); **revoked authorization** — e.g. a connection removed while the
client holds cached bulletins — has no AC. F4 (batch + per-actor ordering) has no AC.

- Implied AC: a mutation with `clientCreatedAt` 31 days old returns `expired` with the user-facing message, and no state changes. *Evidence: quoted response + `SELECT count(*) = 0`.*
- Implied AC: after a connection is removed, the removed peer's cached graph and board entries are purged on next sync and refetch returns 0 rows. *Evidence: quoted sync response + Dexie contents before/after.*
- Implied AC: a batch of 3 mutations from one actor is applied in submission order; a mid-batch failure does not apply later items out of order and each item carries its own outcome. *Evidence: quoted batch response array + quoted row timestamps.*
- Implied AC (retention prune is safe): after the daily prune removes a `mutation_results` row, re-submitting that `mutationId` returns `expired`, **never** a silent duplicate apply. *Evidence: quoted response + `SELECT count(*) = 1` on the effect table.*

### G7 — Bulletin breadth: seven types, Introduction Request, edit, expiry have no AC

Group A is eight work items with essentially zero direct AC coverage. PDF §4 states rules that are
easy to get wrong and currently unspecified: *"Editing does not reset expiry"*, *"Introduction
Requests are directed only to a direct connection who permits them. There is no in-product
forwarding chain"*, and per-type validation for all seven types.

- Implied AC: each of the seven types round-trips create→read with its type-specific required fields, and a payload missing a type-required field is rejected naming the field. *Evidence: seven quoted create responses + one quoted 400.*
- Implied AC: editing a bulletin leaves `expires_at` byte-identical and bumps `version` and `updated_at`. *Evidence: quoted `SELECT` before/after.*
- Implied AC: an expired bulletin is absent from every board and returns `GONE` by ID, without any manual step, within one sweep interval. *Evidence: quoted board response + quoted sweep log line with timestamps.*
- Implied AC: an Introduction Request to a non-direct connection, or to a direct connection who has disabled them, fails closed with a structured code; the recipient cannot forward it. *Evidence: two quoted error responses + the absence of any forward endpoint in the contract surface, quoted.*

### G8 — Graph breadth: degrees ≥ 2 correctness has no AC

PDF §4: *"The product model should not impose an arbitrary depth cap."* Work item B1 delivers
degrees ≥ 2; **only M5-AC3 (ghost payload shape) and M5-AC12 (perf) exist**. Nothing asserts the
traversal returns the *correct* set at depth ≥ 2, that blocks prune inside the recursive term
(ADR-0004, issue #17), or that `path_via` never discloses an unauthorized intermediary.

- Implied AC: on a seeded fixture graph, the viewer's `visible_people` result set equals the hand-computed expected set at depths 1, 2 and 3, including the disclosure level per node. *Evidence: quoted result set beside the quoted expected fixture.*
- Implied AC: a block on an intermediate edge removes every path routed through it at depth ≥ 2 — the downstream nodes reachable only via that edge disappear. *Evidence: quoted result sets before/after the block.*
- Implied AC: `path_via` names only people the viewer is authorized to see; where the intermediary is topology-only, it is a surrogate. *Evidence: quoted `path_via` payload for a viewer with a hidden intermediary.*

### G9 — Views, Notify Me, and notification lifecycle breadth have no AC

A5 (full grammar), A6 (saved views CRUD, defaults, sorts), **A8 (the PDF's "existing matches after
a query change may produce one combined notification" rule)**, C3 (subscription expiry/failure),
C4 (preferences) all have no AC. M2-AC13 covers the *restricted* grammar's rejects only; M5-AC6
covers grouping but not subscription death.

- Implied AC: each of `from: tag: loc: deg: trust: is:` plus negation, alternation, and quoted phrases parses to the expected AST and compiles to a result set matching a hand-computed fixture; each still narrows, never widens (re-run B10 over the full grammar). *Evidence: quoted AST + result counts per operator, plus the B10 assertion output.*
- Implied AC: changing the Notify Me query produces exactly **one** combined notification for pre-existing matches, and zero on subsequent unchanged saves. *Evidence: quoted push payload + count before/after a no-op save.*
- Implied AC: a push endpoint returning 404/410 causes the subscription row to be deleted and no further sends; other devices of the same user still receive. *Evidence: quoted `SELECT` before/after + the second device's captured payload.*
- Implied AC: saved views CRUD is viewer-scoped — user B cannot read, update, or delete user A's view by ID (404, not 403). *Evidence: three quoted responses.*

### G10 — Abuse/rate-limit surface has no AC anywhere

A private trust network with invite tokens, push, and reports has an abuse surface that no AC
touches: invite-token brute forcing, invite-creation flooding, report spam, push-subscription
flooding, sign-in magic-link flooding. M2-AC17 asserts token entropy only.

- Implied AC: N failed invite-token lookups from one IP/actor within the window are rate-limited with 429 and a stable code, and the response for a *valid* token is unchanged in shape from an invalid one. *Evidence: quoted 429 + the two token responses shown identical in shape.*
- Implied AC: a user cannot create more than the configured number of invites or reports per window; the limit is enforced server-side and returns a structured code. *Evidence: two quoted 429 responses.*

### G11 — Observability baseline is under-specified relative to M4.6

M4.6 promises RED metrics per tRPC procedure, an outbox depth/dead-event gauge, and a push failure
rate. **M4-AC5 covers correlation IDs and M4-AC7 covers one alert — the metrics themselves have no
AC.** Addendum §23 lists Observability as one of the fourteen things the slice must prove.

- Implied AC: after driving the smoke suite, the metrics backend returns non-zero rate/error/duration series for at least three named tRPC procedures, plus current outbox depth and push failure rate. *Evidence: screenshot or quoted query result per named series.*
- Implied AC: each of the four M4.7 alert rules fires end-to-end from a synthetic trigger within its stated window (M4-AC7 currently proves one of four). *Evidence: four received-alert screenshots with timestamps.*

### G12 — §25 DoD and the "B5 row per query" rule are asserted but not enforced

M5's preamble states "every new viewer-scoped query adds a row to ADR-0002's B5 matrix — that is
not optional cleanup, it is the item's DoD." Nothing makes that mechanical, so it degrades to a
review convention — exactly the failure mode M1.2 exists to prevent (risk R8).

- Implied AC: a fitness test enumerates viewer-scoped query classes (by directory/naming convention) and fails if any lacks a corresponding B5 matrix row; proven by adding a scratch query and observing the failure. *Evidence: the failing run naming the uncovered query, then the passing run.*

### G13 — Migration failure/rollback has no AC (irreversible-change surface)

M4-AC3 asserts migrations run *before* the API rollout and M4-AC4 rolls back the *application*.
Neither covers a migration that fails mid-apply, or an application rollback whose previous version
cannot read the new schema. Given risk R4 (erasure irreversibility) and the ADR-0002 role split,
this is the highest-consequence unspecified failure mode in M4.

- Implied AC: a deliberately failing migration aborts the deploy, leaves the schema at the prior version (no partial apply), and the previous API version stays serving. *Evidence: quoted migration job output + `/health` showing the prior SHA + quoted `schema_migrations` state.*
- Implied AC: the documented expand/contract rule is exercised once — the previous API version runs green against the new schema. *Evidence: smoke summary line from the N-1 image against the migrated database.*

## Must Fix — sharpness

### S-M1-AC1 — contradicts the milestone's own "Done means"

> "`pnpm install && pnpm typecheck && pnpm lint && pnpm test` exits 0 on a clean clone with no network access to anything but the registry."

**Fails: unambiguous / testable.** M1.3 puts integration tests behind Testcontainers, which needs
Docker and pulls a Postgres image — i.e. network beyond the registry — and the milestone's "Done
means" line requires `pnpm db:reset` first. As written, either `pnpm test` excludes integration
(then the AC proves less than it appears to) or the AC cannot pass.

Sharpened: "`pnpm install && pnpm typecheck && pnpm lint && pnpm test:unit` exits 0 on a clean
clone with no network beyond the npm registry. Separately, `pnpm db:start && pnpm test:integration`
exits 0 with Docker available. *Evidence: two terminal transcripts, exit codes shown.*"

### S-M1-AC4 — vacuously true at M1

> "connecting as `anon` and as `authenticated` and selecting from every table in schema `app` raises SQLSTATE `42501`."

**Fails: falsifiable.** At M1 the baseline migration creates schema `app` and roles; the thirteen
tables arrive in M2.1. "Every table" over an empty set passes trivially — the AC cannot fail even
if grants are wrong. (M1-AC5 avoids this correctly with its scratch-migration proof; AC4 should
mirror it.)

Sharpened: "…raises `42501`, asserted over at least one table created for the purpose in the
baseline migration, and the test fails if `count(*)` of enumerated tables is 0. Proven by granting
`SELECT` to `authenticated` in a scratch migration and observing the failure. *Evidence: the
failing run's assertion message, then the passing run naming each table.*"

### S-M1-AC6 — job count contradicts the work item

> "CI runs all nine jobs on a PR … *Evidence: … a PR checks list showing 9/9 green.*"

**Fails: unambiguous.** M1.6 enumerates **eight** jobs (`typecheck`, `lint`, `lint:boundaries`,
`test:unit`, `test:integration`, `build:web`, `build:server:cloudflare`, `build:server:node`);
appendix issue #7 adds `secret-scan` for nine. A reviewer cannot tell which list is the contract,
and "9/9 green" is satisfiable by any nine checks.

Sharpened: enumerate the nine job names verbatim in the AC, and add the falsifier: "a PR with a
deliberately failing `lint:boundaries` cannot be merged. *Evidence: PR checks screenshot listing
the nine names + a screenshot of the blocked merge button.*"

### S-M1-AC9 — evidence covers half the assertion

> "…is rejected by the hook **and by CI**. *Evidence: quoted hook output on a deliberate test commit (not pushed).*"

**Fails: evidence shape.** The CI half is asserted and then explicitly not evidenced ("not
pushed"). Per the rubric, an unproven half is uncovered.

Sharpened: "…rejected by the hook (local) and by the `secret-scan` CI job. *Evidence: quoted hook
output on a deliberate local commit, plus the CI job's failing output on a throwaway branch pushed
with `--no-verify` and then deleted.*"

### S-M1-AC10 — the evidence cannot detect what the AC asserts

> "No `modules/` subdirectory exists that contains only empty or placeholder files … *Evidence: `find apps/server/src/modules -type d -empty` returns nothing.*"

**Fails: evidence shape / testable.** `-type d -empty` finds only *empty directories*. A directory
containing `index.ts` with `export {}` — the actual §4 violation — passes. Worse, at M1 no
`modules/` directory exists at all, so `find` exits non-zero on a missing path and the AC's
evidence is a failure message.

Sharpened: "A fitness test fails if any directory under `apps/server/src/modules/` contains no file
with a non-trivial export (files whose entire body is comments, `export {}`, or a re-export of
nothing count as placeholders). Proven by adding such a directory and observing the failure.
*Evidence: the failing run naming the offending directory, then the passing run.* At M1 the test
passes trivially and is documented as first load-bearing at M2."

### S-M2-AC4 — requires a filter M2 deliberately does not build

> "The board filter `trust:unset` and `trust:0` select disjoint sets."

**Fails: testable this milestone.** The M2 module table restricts the grammar to `type:` and bare
text; `trust:` is explicitly cut to M5 group A5. This half of the AC cannot be exercised in M2.

Sharpened: split. M2 keeps: "A connection with no trust assigned serializes as `trust: null`; a
deliberately-set `0` serializes as `0`; the database column is NULL vs 0 respectively. *Evidence:
two quoted API responses + one quoted `SELECT trust`.*" Move the filter half to M5 alongside A5,
where `trust:unset` / `trust:0` disjointness becomes an AC of the full grammar.

### S-M2-AC12 — two ambiguities in one line

> "…returns 404/`GONE` by ID for non-authors, while remaining visible to the author under `is:mine`-equivalent access."

**Fails: unambiguous.** (a) "404/`GONE`" is an unresolved alternation — the implementer picks, and
the test asserts whichever was picked, so the AC cannot fail. (b) "`is:mine`-equivalent access" is
undefined and `is:` is M5 grammar; "equivalent" is a weasel word.

Sharpened: "After the author archives: the bulletin is absent from every non-author board and
`bulletins.getById` returns HTTP 404 with code `BULLETIN_GONE` for non-authors; the author's
`bulletins.listMine` still returns it with `archivedAt` set. A second archive returns HTTP 200 and
leaves `archivedAt` unchanged. *Evidence: quoted author and non-author responses before and after,
plus the quoted `archivedAt` value across both archive calls.*"

### S-M2-AC14 — the timing clause is unfalsifiable

> "…returns 0 rows and no error leak (no 'exists but hidden' signal difference in status code or timing shape)."

**Fails: falsifiable.** "Timing shape" names no measurement, no sample size, and no threshold. No
observation can show it failed, so it will be ticked on the status-code half alone. (Constant-time
response is also probably not achievable here and likely not worth buying.)

Sharpened: "A board query referencing an unauthorized bulletin ID and one referencing a
never-existent UUID return byte-identical bodies and identical status codes. *Evidence: quoted
`diff` of the two response bodies, empty.*" If a timing claim is genuinely wanted, make it its own
AC with a method: "p50/p95 over 200 paired requests differ by < 20 ms. *Evidence: quoted latency
table.*" Otherwise drop the clause rather than leave it unmeasurable.

### S-M2-AC17 — entropy and derivation are not observable from the stated evidence

> "The invite token is ≥ 128 bits of entropy, is not derived from any user ID … *Evidence: quoted token + two quoted responses.*"

**Fails: testable / evidence shape.** A quoted token cannot demonstrate entropy, and "not derived
from any user ID" is a property of the generator, not of the artifact. Both halves are
unfalsifiable as stated.

Sharpened: "Token generation calls a CSPRNG with ≥ 16 bytes (asserted by a unit test on the
generator, with a fitness test failing any non-CSPRNG source in that module); 10 000 generated
tokens are all distinct and pass a length/charset assertion; a token generated for user A is not a
prefix/suffix/encoding of A's user ID or handle (asserted directly). A spent or revoked token
returns `INVITATION_UNAVAILABLE`. *Evidence: quoted unit-test output for the generator, quoted
distinctness count, two quoted reuse responses.*"

### S-M5-AC8 — the fitness test is a `grep-finds-string` and the walkthrough is not proof

> "*Evidence: a fitness test grepping response schemas for the forbidden field names, 0 matches, quoted; plus a reviewer walkthrough of the report and person surfaces.*"

**Fails: unambiguous + evidence shape.** The forbidden field names are never enumerated, so the
grep's coverage is whatever the author chose that day — and any new aggregate field with an
unlisted name passes. "Reviewer walkthrough" is a human-verification step being offered as the
agent's proof (rubric: legitimate as a fallback, rejected as evidence).

Sharpened: "A fitness test asserts that no tRPC output schema contains a field whose name matches
the checked-in forbidden list (`reportCount`, `strikes`, `rating`, `score`, `followers`,
`likes`, `reactions`, `popularity`, `endorsements`, `*Count` on a person or bulletin), and the
list file is required by the test to be non-empty. Proven by adding `reportCount` to a schema and
observing the failure. *Evidence: the failing run naming the field, then the passing run; plus
screenshots of the report sheet and person sheet.*"

### S-M5-AC15 — the evidence shape cannot prove the assertion

> "The full M1–M4 AC set still passes on `main` at M5 completion. *Evidence: CI run URL with all jobs green.*"

**Fails: evidence shape.** A large share of M1–M4 ACs are not CI-executable: M1-AC9's hook run,
M4-AC4 (rollback drill), M4-AC5 (log search screenshot), M4-AC7 (alert received), M4-AC10 (backup
restore), M3-AC1/AC2/AC6 (documents and dates). "All jobs green" therefore proves a strict subset
while the AC claims the whole set — the classic green-CI-implies-nothing gap.

Sharpened: split into (a) "every CI-executable M1–M4 AC passes on `main`. *Evidence: CI run URL,
plus the checked-in AC→job mapping table showing which AC each job covers*"; and (b) "each
non-CI-executable M1–M4 AC (enumerate: M1-AC9, M4-AC4, AC5, AC7, AC10) is re-verified manually
within the release window. *Evidence: the dated re-verification transcript/screenshot per AC.*"
The mapping table is the load-bearing artifact — without it, no one can tell which ACs the green
run covered.

## Should Improve

- **M2-AC1** — "drives two browser contexts through every step of the §23 flow and passes" is a paraphrase of the milestone title. A Playwright run can pass having silently skipped a step. Require the eleven §23 steps to be named `test.step()`s and the HTML report to show eleven steps, so a missing step is visible in the artifact.
- **M2-AC7** — the 60 s grouping window has no defined start and no boundary case. Name it: window opens at the first matching event; a second bulletin at t = 59 s groups, one at t = 61 s produces a second notification. Add the boundary pair to the evidence.
- **M2-AC13** — "a 300-character query is rejected; 17 terms are rejected" names only the failing side, so an implementation rejecting everything passes. Name the limits and the passing boundary: 256 chars pass / 257 reject, 16 terms pass / 17 reject (align the numbers with ADR-0007).
- **M2-AC15** — "No SQL string literal exists outside `**/persistence/**`" leaves detection undefined; a naive grep for `SELECT` both false-positives on prose and misses `sql\`` template tags. Name the detection rule (the regex/AST check) and add a violating fixture proving the check fires.
- **M2-AC19** — "the eight new modules" contradicts the M2 module table, which lists nine (identity, connections, graph, bulletins, views, notifications, moderation, sync, audit; storage is explicitly not built). Enumerate them.
- **M3-AC5** — "no hand-rolled crypto, pool, queue, or migration runner introduced by the spike" is a judgment call evidenced by "a listed diff of new dependencies". Make the mechanical half mechanical (lockfile `patchedDependencies` absent — already good) and the judgment half a named reviewer sign-off line in the spike doc, so the two are not conflated.
- **M4-AC1** — `git rev-parse HEAD` on `main` races with any merge landing between deploy and check. Compare against the SHA the deploy job published instead.
- **M4-AC8** — asserts secrets are absent from "the repository, build logs, and the client bundle" but evidences only the bundle grep and the secret-scan job status. Add the build-log grep explicitly.
- **M5-AC1** — "test names must map 1:1 to the twelve rows" is a name-mapping check: twelve well-named tests that assert weakly would tick it. Require each of the twelve to reference the specific AC or invariant it enforces (e.g. row "blocking" → M5-AC2's seven assertions), so the matrix is a coverage index rather than a naming convention.
- **M5-AC12** — "the ADR-0004 synthetic scale" is a cross-reference; inline it (5 000 people, 20 connections each, p95 < 300 ms server-side) so the AC is checkable without opening the ADR, and name what the CI job does on regression.
- **M5-AC13** — "the graph is fully operable by keyboard" uses "fully". Enumerate the operations (focus/traverse nodes, open person sheet, close with Escape, pan, zoom, reach every interactive control in DOM order) so a gap is observable.

## Follow-Up Issues (out of scope)

- **Milestone-weighted AC density.** M1+M2 hold 29 of 61 ACs for roughly 15 % of v1 scope; M5 holds 15 ACs for ~40 work items covering the majority of PDF §3. The systemic fix is a rule — *every M5 work item (A1…G6) carries at least one AC before the item is started* — rather than a flat per-milestone AC list. Consider restructuring M5's AC section as a per-work-item table.
- **No AC traceability index.** Nothing maps AC → CI job → work item, which is what makes S-M5-AC15 unprovable and makes the ADR-0002 B-row coverage gap (G2) invisible. A checked-in `docs/engineering/ac-index.md` regenerated by CI would close this class of finding permanently.
- **Cross-document numeric drift.** Three count mismatches in one document (nine vs eight CI jobs; eight vs nine M2 modules; M2-AC10's "four quoted responses" against three named surfaces). Counts that live in prose drift; prefer enumerating names.
- **ADR-referenced constants are not asserted anywhere.** ADR-0005's 30-day retention, ADR-0006's 8 attempts / 15-minute backoff cap, ADR-0004's 300 ms budget, ADR-0007's length and term limits all appear as prose in ADRs and only sometimes in ACs. A single fitness test asserting the implemented constants equal the ADR-declared values would stop silent divergence.
