# Product decisions log

Decisions delegated to the implementation lead by the product owner (2026-07-30: "I think you can make best decisions here"), resolving spec↔prototype discrepancies. The handoff PDF is authoritative for product behavior; the prototype is product evidence for UX feel.

## D1 — Notify Me is a single saved query (2026-07-30)

Conflict: PDF §4 "one special saved query called Notify Me"; prototype shows a notify bell on every saved view.
Decision: **PDF wins.** Exactly one Notify Me query per user (confirmed by addendum §6's `UpdateNotifyMeQuery`, singular). The prototype's per-view bell becomes the UI affordance for designating *which* view's query is the Notify Me query — toggling a bell on view B moves Notify Me from view A (with clear UI feedback), it does not create a second notifying query.

## D2 — No private notes in v1; bulletin types follow the PDF (2026-07-30)

Conflict: prototype has a "private note to a person's board" compose mode (type `note`, audience "Only <name>"); PDF's bulletin type list is Offer, Request, Event, Collaboration, Appreciation, Network Update, Introduction Request — no `note` — and v1 explicitly excludes native messaging.
Decision: **Cut private notes from v1.** They are fixed-recipient messaging in disguise, which the PDF both excludes and flags for a separate future evaluation (§6 "A future fixed-recipient private messaging feature… must not be silently mixed into the bulletin model"). Implement the PDF's seven types, including Network Update. The compose sheet's note mode is not built.

## D3 — Operator moderation; "stewards" allowed as UI copy only (2026-07-30)

Conflict: prototype report-sheet copy promises "stewards will review"; PDF specifies single-operator moderation with no report aggregation and no outcome visibility.
Decision: **Implement operator moderation exactly per PDF §5 and addendum §16.** UI copy may use community-toned language ("stewards") if final copy wants it, but it must not promise review timelines, outcomes, or community juries. Default copy: "Your report was sent privately for review."

## D4 — Notifications entry is a drawn bell, not the comp's ◔ glyph (2026-08-10, owner-directed)

Conflict: the comp (`design/Playa Post.dc.html`) draws the notifications button's mark as the text glyph ◔; owner directive #91 says the entry "should actually be a little bell icon."
Decision: **Owner wins — inline SVG bell.** ◔ does not read as notifications at a glance, and an emoji bell cannot take the theme's ink colour; an inline SVG stroked in `currentColor` and sized in `em` follows `.icon-button`'s theme ink and font-size scaling like the glyph it replaced. Scope: a one-off override, not the start of an icon migration — the remaining chrome glyphs (☾/☀ theme toggle, tab bar, graph zoom) stay text glyphs until a reason arrives. If a second drawn icon lands, decide the chrome icon convention first (the precedent set here: inline SVG, `currentColor` stroke, `em`-sized) and consider a shared icon module at the third.

## D5 — Six postable types; Network Update is system-written, label-only typing for now (2026-08-10)

Conflict: D2 adopts the PDF's seven bulletin types including Network Update, but the prototype's compose surface offers only six (`design/Playa Post.dc.html:892` — no `update` chip), and nothing in v1 scope produces a network update.
Decision: **The postable set is the prototype's six** — offer, request, event, collab, thanks, intro. `update` remains a member of the board grammar's `type:` vocabulary (ADR-0007) so the filter parses, but no person can compose one: a network update is something the *system* writes when that feature arrives, and until it does, `type:update` resolves to an empty board rather than an error. `create` refuses `update` (and `note`, per D2) by naming the field. Corollary, recorded so the model is deliberate rather than accidental: in M5 a bulletin's type is a *label* — classification, tint, and filter key — with no per-type structure (an `event` has no start time; `expiresAt` remains visibility-end for every type). The day a type grows structure, that is a discriminated-union change with its own decision, not a silent widening.

## D6 — Private notes are back, as a separate module and never a bulletin type (2026-08-10, owner-directed)

Conflict: **D2 cut private notes from v1**; the owner directive behind [#88](https://github.com/drewdrewthis/playa-post/issues/88) reopens them ("Pin a note").
Decision: **Owner wins on the feature; the PDF still wins on the shape.** D2's *reasoning* was never that notes are unwanted — it was PDF §6: "A future fixed-recipient private messaging feature… must not be silently mixed into the bulletin model." That constraint is unchanged, so the feature returns only in the form that honours it, and the separation is structural rather than a naming convention:

- its own table (`app.notes`) and its own authorized set (`app.visible_notes`), which composes `app.visible_people` for the author card only — the authorization is `recipient_id = viewer_id`;
- its own module (`modules/notes`) and its own router, mounted **beside** `bulletins`, never inside it;
- `bulletins.create` still refuses the value `note`, and `bulletin-post-types.feature`'s refusal scenario is deliberately untouched;
- notes never enter the **bulletin board query**, a saved-view query, or the free-text haystack. There is no tsvector over `app.notes`, so no grammar can ever reach a note's text. What the recipient's board *does* do is load `app.visible_notes` as a **second, separate read** and interleave the two kinds of card by time — one screen, two queries, and the notes half is dropped entirely the moment a query or a saved view is active, because a note must never be something a search can return. The separation D6 is defending is of the *query surface*, not of the pixels: mixing notes into `app.visible_bulletins` would make a note reachable by the grammar, whereas showing them side by side does not.

**Degree 1 is the only gate.** A note may be pinned to a first-degree connection and to nobody else, and the check lives inside the insert statement (`INSERT … SELECT … WHERE EXISTS` over `app.visible_people`), so a refusal writes no row. "Not connected", "two hops away", "no such person", "no longer active", and "that is yourself" are one indistinguishable refusal (`NOTE_RECIPIENT_UNREACHABLE`, HTTP 404) — a product with no people search cannot afford an endpoint that confirms who exists.

**A delivered note is the recipient's, and only the author *card* is revocable.** Degree 1 gates the *pinning*; nothing re-derives it at read time. Once a note is delivered, severing the connection, the author deactivating, or the author lowering their disclosure may each change what the recipient is told about **who wrote it** — down to and including being told nothing, not even a user ID — and none of them removes **what they were told**. `app.visible_notes` therefore LEFT-joins `app.visible_people` and projects every author column from that set, which is the one place notes deliberately diverge from bulletins: a bulletin is published outward and rightly leaves with its author, whereas a note was addressed and handed over. The alternative — an INNER join, so a note silently disappears off somebody's board because a third party changed a setting — is this product quietly editing what a person was told, and is a worse failure than an unattributed note. A client renders an authorless note with no author line and never a reconstructed one.

**Deferred, pending an owner decision: the comp's "WHO CAN PIN TO YOUR BOARD" control.** The comp offers a three-valued trust/distance pair for it, which contradicts its own degree-1 gate — if only direct connections can pin, a "second degree" or "anyone" setting has nothing to widen to, and a trust threshold is a different axis again (trust is private and directional, ADR-0004 decision 6, so a threshold would leak the setter's private number through who succeeds at pinning). Rather than guess which of those the control means, the recipient-side limit is not built: degree 1 is the whole rule for now. This is a UX and trust-model question, which addendum §24 sends back to the owner.

Corollary: a note has no update and no take-down in this slice, so `app.notes` carries neither a `version` nor an `archived_at` column. Both arrive with the mutation that needs them (addendum §4 forbids the placeholder), and `version` specifically arrives with the first mutation ADR-0005 marks `expectedVersion: yes`.

## D7 — "Seen" fires the moment the notifications panel opens, not per notification scrolled into view (2026-08-11)

Conflict: [#178](https://github.com/drewdrewthis/playa-post/issues/178) says the bell badge must fall when a person opens their notifications panel, without making them dismiss each row. "Opened it" admits two readings — the panel opened, or each notification was actually scrolled onto the screen — and the ACs deliberately ask for the choice to be recorded rather than assumed.

Decision: **the panel opening is the event.** One `notifications.markSeen` per opening, advancing a single per-person watermark (`app.notification_seen_watermarks.last_seen_at`); `notifications.list` then serves `seen` as `occurredAt <= last_seen_at`. Scroll-into-view would need an IntersectionObserver per row, a client-sent list of identifiers, and a rule for a row that was half on screen — for no user-visible difference at the list sizes this product produces, where the panel is a full-column takeover and opening it puts essentially the whole list in front of the reader. Addendum §24's "simplest proven implementation" resolves it, and the watermark also asks the client for nothing it would have to be trusted on: no identifier list, one O(1) write per opening. Accepted consequence: the mark covers everything up to the server's clock at write time — including a notification delivered after the client's last read, which an id list would not have named. That over-mark is fine because the panel is open and polling at that moment, so what the mark covers is what the reader is being shown.

**Seen is not dismissed, and the two states stay separate on purpose.** Seen answers "has anything happened since you last looked" and is the *only* thing the badge counts (`unread && !seen`); dismissed answers "have you dealt with this" and is the only thing that moves a row out of the panel's active section. Opening the panel therefore changes nothing on screen — every row the reader came for is exactly where it was — which is why the badge and the panel could be given one flag each rather than one flag between them. All four combinations are reachable and each means something.

Corollaries, recorded so the model is deliberate rather than accidental:

- **The comparison is inclusive.** A notification stamped at the exact instant of an open counts as seen: it was on the list the reader was shown, and an exclusive comparison would leave that one row holding the badge up forever, because no later open can move a watermark past a timestamp it equals.
- **The watermark only moves forward**, enforced in the upsert rather than by the caller. Two devices with disagreeing clocks, or a retry arriving late, must never un-see notifications somebody has already been shown.
- **`markSeen` is deliberately not idempotent**, unlike `notifications.dismiss`, which converges on its first timestamp. "I am looking now" is true of every call, and a converging watermark would freeze at the first open and never clear a badge again. Repeating it is still safe.
- **No outbox event**, matching the dismissal decision and for a stronger version of its reason: opening a panel has no reactor, and an audit entry would durably record every time a person glanced at their own bell.
- **A per-device watermark is a future decision, not a future default.** The primary key is `recipient_id`, so today two devices share one badge — which is the behaviour a person expects from a badge that means "since you last looked", regardless of which screen they last looked at.

## D8 — A dismissed push offer is remembered per device, and made again after 30 days (2026-08-11)

Conflict: [#167](https://github.com/drewdrewthis/playa-post/issues/167) says the notifications panel must stop offering push to a device that already has it, and must stop re-offering it to somebody who closed the browser's permission dialog without answering. Enrolment needs no decision — it is recoverable from the browser, because a held subscription is a fact `pushManager.getSubscription()` will state on request. A **dismissal** is not: the Push API records nothing when a person waves the prompt away, so "this one was asked and said not now" exists only if the app writes it down, and where it is written decides who it is true of.

Decision: **write it on the device, in `localStorage`, and make the offer again after 30 days.**

**Device-local, because push enrolment is itself a device fact.** A subscription lives in one browser's own service worker registration; the same person on a phone and a laptop is two enrolments or one, and the server cannot tell which — `app.push_subscriptions` is keyed on `owner_id`, one row per person, so it could not answer "is *this* device enrolled" even if asked. The answer "not on this device, thanks" is therefore a device answer too. An account-level record would suppress the offer on a new device where it has never been made, which is the opposite of the bug being fixed: a person who declined on a laptop in April would install the PWA on their phone in August and never be offered the notifications they came for.

**Two facts at most, and a device may never hold both.** The marker keeps the VAPID public key this device enrolled under (the key, not a boolean — a subscription is bound for life to the key that minted it, so after the rotation `docs/engineering/secrets.md` §4 prescribes, "subscribed" under the superseded key is not subscribed) and the time the prompt was last dismissed. Enrolling clears the dismissal, because the device has now answered yes to the question that recorded one.

**The marker is a hint for the first paint; the browser is the authority.** The panel reads enrolment twice — synchronously from the marker, so a device that enrolled last week paints "Push is on for this device." on the first frame instead of flashing consent copy at somebody who has already consented, and then again a tick later from the subscription the browser is actually holding, which corrects and reconciles it. Nothing is ever *believed* over the browser. That is what makes the storage safe to be wrong: it can only ever be wrong for one frame.

**A cooldown, not a retirement.** Dismissing a browser permission dialog is as often a stray tap or an Escape as a decision, and "clear this site's data" is not a path back anybody will find. Accepted consequence, in both directions: somebody who meant it is offered push again in a month, in a panel they only reach by choosing to look at their notifications; somebody who changes their mind either presses again before leaving the panel — the control is unchanged within the session, so a second press asks again — or waits up to 30 days. No settings screen is built for this, and none should be until something else needs one.

Corollaries, recorded so the model is deliberate rather than accidental:

- **A granted permission outranks a recorded dismissal.** The dismissal records "the browser asked and got no answer"; a permission that is now `granted` means the question has since been answered yes, in the browser's own settings. So the offer returns immediately in that case rather than waiting out the cooldown — it is the one quick way back for somebody who changed their mind, and honouring the dismissal there would leave them none.
- **A browser block is still named, ahead of the dismissal.** Chrome blocks an origin by itself after repeated dismissals, so "dismissed, then blocked" arrives without anybody choosing it. The panel says so, with the copy that names the browser settings as the only remedy, rather than going quiet and leaving a reader wondering why the app never mentions push.
- **Revoking permission un-enrols the device on the next load.** Permission is checked before the held subscription is even looked at, so neither the marker nor a subscription the browser has not got round to dropping can keep the enrolled line on screen. The stale marker is cleared as it goes, so the correction survives the reload rather than being re-made every time.
- **"Cannot see" is not "not enrolled".** With no service worker registered — a `pnpm dev` run, or the seconds a fresh install spends registering one — nothing is claimed and nothing is forgotten. A settled read that answered "not enrolled" there would clear a working device's marker on a race.
- **Unavailable storage costs a flash, never a failure.** A locked-down profile throws on `localStorage` access; every read and write is guarded, an unreadable marker reads as empty, and correctness is unaffected because the subscription is still the authority. That device pays one frame of consent copy per panel opening.

## D9 — The bulletin-removal action is called "Remove"; removed bulletins stay visible to their author (2026-08-11, owner-directed)

Conflict: [#168](https://github.com/drewdrewthis/playa-post/issues/168) — the owner asked that "Archive should be remove and can be soft deleted." The action already soft-deletes (`Bulletin.archivedAt`), so only the name was wrong; but renaming reopened whether a removed bulletin should keep appearing, marked, on its author's own board.

Decision: **rename the copy only; keep the current visibility semantics.** Every user-facing surface of this action now says "Remove"/"Removed" — the detail sheet's button, the card's pill, the offline sync queue's row label, and the report-own-bulletin refusal copy. The mechanism is unchanged: `archivedAt` soft delete, no hard delete, and a removed bulletin remains visible to its author, marked as removed, exactly as before. Any change to those semantics — including whether removal should eventually hide the bulletin from its author, and how long soft-deleted rows live — is deferred to [#169](https://github.com/drewdrewthis/playa-post/issues/169) (uniform soft delete + purge), which owns that model as a whole. Internal identifiers (`archivedAt`, `bulletins.archive`, `bulletin-archive-button`, `data-archived`) keep their names: they describe the mechanism, not the copy, and renaming them would churn the API contract and stored offline mutations for no user-visible gain.

## D10 — One rejected-code message, not two: GoTrue cannot tell wrong from expired from reused (2026-08-11)

Conflict: [#179](https://github.com/drewdrewthis/playa-post/issues/179)'s ACs ask for an incorrect code's failure state to be "distinct from an expired code," and separately for an expired code to tell the user to request a new one — two bullets that read as two different user-facing messages. Supabase's GoTrue answers a wrong digit, an expired code, and an already-spent code with the identical signal: HTTP 403, `error_code: otp_expired`. Verifying a code is one lookup against one stored token, and all three causes leave that lookup with nothing to find — there is no field on the wire, and no accompanying data, that says which of the three happened.

Decision: **one honest message, not two guessed ones.** `describeSignInFailure` maps `otp_expired` to a single string naming all three possible causes and the one remedy that fixes all of them: "That code did not match — it may be mistyped, expired, or already used. Request a new sign-in email and enter the fresh code." The alternative — inferring "expired" vs. "wrong" from, say, elapsed time since the code was requested — was considered and rejected: it is a client-side guess about server-side state (the actual OTP expiry window, clock skew, a resend that reset the window), it can only drift out of sync with the real expiry as either side changes independently, and a wrong guess is worse than no guess — it would tell someone their code was "wrong" when they had in fact typed the right one too late, sending them to retype a code that could never work rather than to request a new one. AC4's "distinct from an expired code" is satisfied at the level the ACs actually gate: this is its own named branch in `sign-in-failure.ts`, tested on its own, and never falls through to the generic refusal — it is distinct from a rate limit, from a misconfigured build, and from the generic catch-all. It is not distinct from AC5's expired-code case, because nothing this app can see is either.

Corollary: this also answers AC6 (a spent code cannot be reused) implicitly rather than with a dedicated user-facing state — a reused code fails through the exact same branch, with the exact same message, because to GoTrue it is the exact same shape of failure as an expired one. There is nothing further to build for AC6 beyond what the provider already enforces.

## D11 — Passing an intro on requires the via's own note; a decline carries none (2026-08-11, owner-directed)

Conflict: [#175](https://github.com/drewdrewthis/playa-post/issues/175) — the owner asked that a via who passes an introduction on must add something of their own: "you have to add your own message." Issue [#89](https://github.com/drewdrewthis/playa-post/issues/89) shipped `intros.decide` as a bare decision with no content on either branch, and the target saw exactly one note: the requester's. The directive reopens what a pass-on *is*, and with it three questions #89 never had to answer — whether the note is required or offered, who reads it, and what a decline does with the same field.

Decision: **required on `pass_on`, forbidden on `decline`, and the target reads both notes with both authors named.**

**Required, not offered, because a pass-on is a vouch rather than a forward.** The whole premise of the one-hop introduction is that meeting a stranger goes *through* somebody who knows you both — and an intro passed on with nothing added is that person's name attached to a shrug. Making the note optional would have produced exactly the state the feature exists to prevent: a target reading a stranger's ask, seeing a mutual connection's name beside it, and being unable to tell whether that person actually thought it was a good idea. The requirement is the difference between a relay and an endorsement.

**The target sees two notes, each under its own author's card**, and never one joined paragraph. `IntroInboxRow` carries `note` (the requester's) and `viaNote` (the via's) as separate fields for that reason: attributing a vouch to the person being vouched for is the one misreading this screen must not permit, and a client that received one string could not avoid it. The via's card is projected from `app.visible_people(via, 0, 1)` — their own self-projection — which is the same **consent inversion** the requester's card already rests on, extended one person: *choosing to pass an introduction on is choosing to be seen by the target as its via.* It has to be, now that the via has words of their own on the row; a signature that disappears when the via's connection to the target lapses would leave an unattributed vouch behind, which is worse than no vouch.

**A decline carries no note, and one sent with a decline is refused rather than dropped.** The requester is told only that it was not passed on — no reason, no re-ask control (D6's sibling rule, `INTRO_NOT_PASSED_ON_LINE`) — so text written on a decline has no reader at all. Accepting the field and discarding it silently would let its writer believe otherwise, which is why `decideIntroInput`'s decline branch is a `strictObject` — over tRPC the refusal is the wire's own plain `BAD_REQUEST`, no application code — and why the domain keeps `INTRO_DECLINE_CARRIES_NO_NOTE` as its own backstop code for callers that bypass the wire, rather than a second meaning for `INTRO_CONTENT_INVALID`.

**The enforcement is deliberately split between the database and the domain, and the halves say different things.** `app.intro_requests.via_note` carries `check (via_note is null or status = 'passed_on')` — an *implication*, not the biconditional `intro_requests_decided_at` uses beside it. "Only a passed-on request may carry a via note" is true forever; "every passed-on request carries one" is not, because rows passed on before this migration have none and migrations are forward-only. So the database states what is possible for all time, and `domain/intro-note.policy.ts`'s `validateViaNote` states what is required *now* — on every new pass-on. A plain biconditional CHECK would have refused to apply against the pre-feature rows; Postgres's `not valid` variant would have applied by skipping them, at the price of a schema permanently asserting a requirement the stored data does not meet, validated nowhere.

Corollaries, recorded so the model is deliberate rather than accidental:

- **The via cannot read their own note back, and neither can the requester.** It is on the target's inbox row and nowhere else — not on `intros.listOutbox`, not on the decide receipt, not in an outbox event payload. That is a stronger rule than the one the requester's note is held to rather than the same one twice: the via wrote those words *to* the target, *about* the requester, and showing them to the requester would turn a vouch into something the person being vouched for reads over the writer's shoulder. Nobody writes an honest one twice.
- **The bound is the requester's bound**, 1–4000 after trimming, from the same constant and the same policy file. Both notes land in `text` columns on one row and are read on one screen, so a via allowed more room than the person they are vouching for would be a rule nobody chose.
- **Absent and empty are one refusal.** A pass-on with no `note` field and one with `''` are the same fact about what the target would read, so both answer `INTRO_CONTENT_INVALID` rather than getting a code each. The wire schema's `min(1)` is about the union being honest — the branch that says "this one has a note" must not accept a request with none in it — and trimming stays the domain's, because that is where its refusal code lives.
- **Introductions passed on before this shipped keep working, unsigned.** Their rows carry `via_note = null`, the wire omits the key, and the client renders the requester's half alone. There is no placeholder: an empty quote attributed to somebody is worse than a note they never wrote.

## D12 — Accepting an introduction is a token-free mutation, and the connection is formed from a published event (2026-08-12)

Conflict: [#166](https://github.com/drewdrewthis/playa-post/issues/166) — a passed-on introduction had no answer. The target's row rendered read-only while the via's carried controls, and `modules/intros/domain/intro-request.ts` recorded that post-`passed_on` action was deliberately out of scope for [#89](https://github.com/drewdrewthis/playa-post/issues/89) because "minting a connection from an intro is a new authorization path". The issue left the mechanism explicitly unresolved: **mint a bearer invite token and reuse `connections.acceptInvite`, or add a token-free mutation.** Connections had exactly one way to form until now, and this makes a second, so the choice is a trust-model decision rather than an implementation detail.

Decision: **a token-free `intros.respond`, authorized by the caller's own resolved actor; the connection is written by `modules/connections` from an `IntroAccepted` outbox event.**

**Token-free, because a minted bearer token would be an unaddressed artifact solving a problem we do not have.** The caller's identity is already authenticated at the tRPC boundary and the row already names its target, so `where target_id = <actor> and status = 'passed_on'` is a complete authorization in one statement. A token, by contrast, arrives with a fourth set of questions nobody asked: where it is stored, how long it lives, what revokes it, what happens when it leaks, and what a second person holding it may do. `app.invitations` answers those for a *transferable* claim — an invite is meant to be handed to somebody unnamed, which is exactly why it is bearer-shaped. An introduction names all three parties at the moment it is written; making it transferable would let the one thing the one-hop design forbids happen, which is somebody outside the triangle acting on it.

**The consent inversion (ADR-0017 D4/D8) is preserved rather than stretched.** Every party has already consented in their own act by the time this mutation is reachable: the requester consented by asking (and was told, before send, that asking is consent to be seen), the via consented by passing it on with a note under their own name, and the target consents here by accepting. Nothing new is disclosed at acceptance — the target has already read both notes and both cards — so this adds a *write* to the model, not a disclosure.

**The connection is formed from an event, not from a call, and that is the load-bearing half.** `modules/intros` writes `status = 'accepted'` and `IntroAccepted` in one transaction; `modules/connections` subscribes to that event and writes the edge under its own `app.consumer_receipts` row. Two properties follow that a direct call cannot provide:

- **A crash cannot lose the connection.** A synchronous call would put the acceptance and the edge in two transactions, and a failure between them leaves an introduction that says `accepted` with no connection — unrecoverable, because answering is terminal-once and nobody may retry. With the outbox the failure mode is a delivery still owed, which is precisely what ADR-0006's retry and dead-letter path already handles.
- **`app.connections` keeps one writer.** Cross-module row creation is what addendum §19 forbids and `sql-table-ownership` polices; `modules/intros` never learns `modules/connections` exists, and the two modules' only coupling is the event *name*.

The price is honest and small: the edge lands on the drainer's next round rather than instantly, so the acceptance confirmation says "you are being connected" rather than claiming it is done, and the e2e polls a reloaded graph. A UI that promised an instantaneous connection would have been the version of this that lies.

**The target's answer needs its own vocabulary, in two places.** The status is `target_declined` rather than a second use of `declined`: that one says the via would not pass it on and the target was never told, this one says the target read it and said no, and collapsing them would silently widen every read that filters on the first. The timestamp is `responded_at` rather than a reused `decided_at`: they belong to two different people, the interval between them is the only record of how long an introduction sat unanswered, and `IntroAccepted.occurredAt` reads the target's — an acceptance stamped with the via's time would claim the target answered before they were shown anything.

Corollaries, recorded so the model is deliberate rather than accidental:

- **A target's decline is invisible to the requester, and indistinguishable from an introduction nobody has answered yet.** This is ADR-0017's founding invariant applied one person along: somebody who can be *seen* refusing cannot safely refuse, and an introduction is worth nothing if the person receiving it is under obligation. `intros.listOutbox` therefore reports the **via's** decision only — `accepted` and `target_declined` both read back there as `passed_on` — and carries no answer time. An acceptance still reaches the requester, because it discloses itself by connecting, which is the target's own act rather than the read's.
- **The same refusal answers every reason, including "the via declined it".** `INTRO_UNAVAILABLE` covers not-yours, already-answered, still-open and via-declined alike. A distinct refusal for the last one would let a target detect a decline simply by trying to accept it, reopening from the other side the exact oracle the feature closed.
- **Eligibility is deliberately not re-checked on the answer**, unlike a pass-on (ADR-0017 D3). A pass-on re-asks the graph because it is about to disclose the requester to somebody; an answer discloses nothing new, because the target has already read the introduction. Refusing it now would withdraw nothing and would strand somebody holding an introduction they can neither accept nor refuse.
- **An accepted introduction produces exactly the connection an accepted invite produces** — `accepted`, `full` both ways, from the columns' own defaults, and no trust row. An intro-formed connection that disclosed differently would be a second connection model nobody chose. `ConnectionAccepted` carries `introRequestId` where an invite-formed one carries `invitationId`, as one union rather than two event types: "these two are now connected" is one fact whoever caused it, and a second type would mean every future consumer had to remember to subscribe twice.
- **Introductions passed on before this shipped are answerable.** They carry `responded_at = null` and status `passed_on`, which is exactly the state the new mutation acts on. The two CHECKs that had to move did so for that reason: `intro_requests_status` widened to five values, and `intro_requests_via_note` — written when `passed_on` was terminal — would otherwise have refused the very UPDATE that accepts an introduction carrying a vouch.
