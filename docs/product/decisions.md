# Product decisions log

Decisions delegated to the implementation lead by the product owner (2026-07-30: "I think you can make best decisions here"), resolving spec↔prototype discrepancies. The handoff PDF is authoritative for product behavior; the prototype is product evidence for UX feel.

## D1 — Notify Me is a single saved query (2026-07-30) — ⚠ **superseded in part by [D16](#d16--notify-me-is-a-set-capped-at-six-d1s-single-query-rule-is-reopened-2026-08-12-owner-directed)**

Conflict: PDF §4 "one special saved query called Notify Me"; prototype shows a notify bell on every saved view.
Decision: **PDF wins.** Exactly one Notify Me query per user (confirmed by addendum §6's `UpdateNotifyMeQuery`, singular). The prototype's per-view bell becomes the UI affordance for designating *which* view's query is the Notify Me query — toggling a bell on view B moves Notify Me from view A (with clear UI feedback), it does not create a second notifying query.

⚠ **The count is no longer this.** D16 (owner-directed, [#172](https://github.com/drewdrewthis/playa-post/issues/172)) reopens the single-query rule: several bells may be lit at once, capped per person. What survives is everything else D1 settled — the bell is a *designation*, `app.notify_me_queries` is the sole answer to "who gets notified", and no notify flag lives on a saved view. Read D16 before implementing against this entry.

## D2 — No private notes in v1; bulletin types follow the PDF (2026-07-30)

Conflict: prototype has a "private note to a person's board" compose mode (type `note`, audience "Only <name>"); PDF's bulletin type list is Offer, Request, Event, Collaboration, Appreciation, Network Update, Introduction Request — no `note` — and v1 explicitly excludes native messaging.
Decision: **Cut private notes from v1.** They are fixed-recipient messaging in disguise, which the PDF both excludes and flags for a separate future evaluation (§6 "A future fixed-recipient private messaging feature… must not be silently mixed into the bulletin model"). Implement the PDF's seven types, including Network Update. The compose sheet's note mode is not built.

## D3 — Operator moderation; "stewards" allowed as UI copy only (2026-07-30)

Conflict: prototype report-sheet copy promises "stewards will review"; PDF specifies single-operator moderation with no report aggregation and no outcome visibility.
Decision: **Implement operator moderation exactly per PDF §5 and addendum §16.** UI copy may use community-toned language ("stewards") if final copy wants it, but it must not promise review timelines, outcomes, or community juries. Default copy: "Your report was sent privately for review."

## D4 — Notifications entry is a drawn bell, not the comp's ◔ glyph (2026-08-10, owner-directed)

Conflict: the comp (`design/Playa Post.dc.html`) draws the notifications button's mark as the text glyph ◔; owner directive #91 says the entry "should actually be a little bell icon."
Decision: **Owner wins — inline SVG bell.** ◔ does not read as notifications at a glance, and an emoji bell cannot take the theme's ink colour; an inline SVG stroked in `currentColor` and sized in `em` follows `.icon-button`'s theme ink and font-size scaling like the glyph it replaced. Scope: a one-off override, not the start of an icon migration — the remaining chrome glyphs (☾/☀ theme toggle, tab bar, graph zoom) stay text glyphs until a reason arrives. If a second drawn icon lands, decide the chrome icon convention first (the precedent set here: inline SVG, `currentColor` stroke, `em`-sized) and consider a shared icon module at the third.

## D5 — Six postable types; Network Update is system-written, label-only typing for now (2026-08-10)

Conflict: D2 adopts the PDF's seven bulletin types including Network Update, but the prototype's compose surface offers only six (`design/Playa Post.dc.html:892` — no `update` chip), and nothing in v1 scope produces a network update.
Decision: **The postable set is the prototype's six** — offer, request, event, collab, thanks, intro. `update` remains a member of the board grammar's `type:` vocabulary (ADR-0007) so the filter parses, but no person can compose one: a network update is something the *system* writes when that feature arrives, and until it does, `type:update` resolves to an empty board rather than an error. `create` refuses `update` (and `note`, per D2) by naming the field. Corollary, recorded so the model is deliberate rather than accidental: in M5 a bulletin's type is a *label* — classification, tint, and filter key — with no per-type structure (an `event` has no start time; `expiresAt` remains visibility-end for every type). The day a type grows structure, that is a discriminated-union change with its own decision, not a silent widening.

## D6 — Private notes are back, as a separate module and never a bulletin type (2026-08-10, owner-directed)

Conflict: **D2 cut private notes from v1**; the owner directive behind [#88](https://github.com/drewdrewthis/playa-post/issues/88) reopens them ("Pin a note").
Decision: **Owner wins on the feature; the PDF still wins on the shape.** D2's *reasoning* was never that notes are unwanted — it was PDF §6: "A future fixed-recipient private messaging feature… must not be silently mixed into the bulletin model." That constraint is unchanged, so the feature returns only in the form that honours it, and the separation is structural rather than a naming convention:

- its own table (`app.notes`) and its own authorized set (`app.visible_notes`), which composes `app.visible_people` for the author card only — the authorization is `recipient_id = viewer_id`;
- its own module (`modules/notes`) and its own router, mounted **beside** `bulletins`, never inside it;
- `bulletins.create` still refuses the value `note`, and `bulletin-post-types.feature`'s refusal scenario is deliberately untouched;
- notes never enter the **bulletin board query**, a saved-view query, or the free-text haystack. There is no tsvector over `app.notes`, so no grammar can ever reach a note's text. What the recipient's board *does* do is load `app.visible_notes` as a **second, separate read** and interleave the two kinds of card by time — one screen, two queries, and the notes half is dropped entirely the moment a query or a saved view is active, because a note must never be something a search can return. The separation D6 is defending is of the *query surface*, not of the pixels: mixing notes into `app.visible_bulletins` would make a note reachable by the grammar, whereas showing them side by side does not.

**Degree 1 is the only gate.** A note may be pinned to a first-degree connection and to nobody else, and the check lives inside the insert statement (`INSERT … SELECT … WHERE EXISTS` over `app.visible_people`), so a refusal writes no row. "Not connected", "two hops away", "no such person", "no longer active", and "that is yourself" are one indistinguishable refusal (`NOTE_RECIPIENT_UNREACHABLE`, HTTP 404) — a product with no people search cannot afford an endpoint that confirms who exists.

**A delivered note is the recipient's, and only the author *card* is revocable.** Degree 1 gates the *pinning*; nothing re-derives it at read time. Once a note is delivered, severing the connection, the author deactivating, or the author lowering their disclosure may each change what the recipient is told about **who wrote it** — down to and including being told nothing, not even a user ID — and none of them removes **what they were told**. `app.visible_notes` therefore LEFT-joins `app.visible_people` and projects every author column from that set, which is the one place notes deliberately diverge from bulletins: a bulletin is published outward and rightly leaves with its author, whereas a note was addressed and handed over. The alternative — an INNER join, so a note silently disappears off somebody's board because a third party changed a setting — is this product quietly editing what a person was told, and is a worse failure than an unattributed note. A client renders an authorless note with no author line and never a reconstructed one.

**Deferred, pending an owner decision: the comp's "WHO CAN PIN TO YOUR BOARD" control.** The comp offers a three-valued trust/distance pair for it, which contradicts its own degree-1 gate — if only direct connections can pin, a "second degree" or "anyone" setting has nothing to widen to, and a trust threshold is a different axis again (trust is private and directional, ADR-0004 decision 6, so a threshold would leak the setter's private number through who succeeds at pinning). Rather than guess which of those the control means, the recipient-side limit is not built: degree 1 is the whole rule for now. This is a UX and trust-model question, which addendum §24 sends back to the owner.

Corollary: a note has no update and no take-down in this slice, so `app.notes` carries neither a `version` nor an `archived_at` column. Both arrive with the mutation that needs them (addendum §4 forbids the placeholder), and `version` specifically arrives with the first mutation ADR-0005 marks `expectedVersion: yes`.

## D7 — "Seen" fires the moment the notifications panel opens, not per notification scrolled into view (2026-08-11)

Conflict: [#178](https://github.com/drewdrewthis/playa-post/issues/178) says the bell badge must fall when a person opens their notifications panel, without making them dismiss each row. "Opened it" admits two readings — the panel opened, or each notification was actually scrolled onto the screen — and the ACs deliberately ask for the choice to be recorded rather than assumed.

Decision: **the panel opening is the event.** One `notifications.markSeen` per opening, advancing a single per-person watermark (`app.notification_seen_watermarks.last_seen_at`); `notifications.list` then serves `seen` as `occurredAt <= last_seen_at`. Scroll-into-view would need an IntersectionObserver per row, a client-sent list of identifiers, and a rule for a row that was half on screen — for no user-visible difference at the list sizes this product produces, where the panel is a full-column takeover and opening it puts essentially the whole list in front of the reader. Addendum §24's "simplest proven implementation" resolves it, and the watermark also asks the client for nothing it would have to be trusted on: no identifier list, one O(1) write per opening. Accepted consequence: the mark covers everything up to the server's clock at write time — including a notification delivered after the client's last read, which an id list would not have named. That over-mark is fine because the panel is open and polling at that moment, so what the mark covers is what the reader is being shown.

**Seen is not dismissed, and the two states stay separate on purpose.** Seen answers "has anything happened since you last looked" and is the *only* thing the badge counts (`unread && !seen`); dismissed answers "have you dealt with this" and is the only thing that moves a row out of the panel's active section. Opening the panel therefore changes nothing on screen — every row the reader came for is exactly where it was — which is why the badge and the panel could be given one flag each rather than one flag between them. All four combinations are reachable and each means something.

Corollaries, recorded so the model is deliberate rather than accidental:

- **The comparison is inclusive.** A notification stamped at the exact instant of an open counts as seen: it was on the list the reader was shown, and an exclusive comparison would leave that one row holding the badge up forever, because no later open can move a watermark past a timestamp it equals.
- **The watermark only moves forward**, enforced in the upsert rather than by the caller. Two devices with disagreeing clocks, or a retry arriving late, must never un-see notifications somebody has already been shown.
- **`markSeen` is deliberately not idempotent**, unlike `notifications.dismiss`, which converges on its first timestamp. "I am looking now" is true of every call, and a converging watermark would freeze at the first open and never clear a badge again. Repeating it is still safe.
- **No outbox event**, matching the dismissal decision and for a stronger version of its reason: opening a panel has no reactor, and an audit entry would durably record every time a person glanced at their own bell.
- **A per-device watermark is a future decision, not a future default.** The primary key is `recipient_id`, so today two devices share one badge — which is the behaviour a person expects from a badge that means "since you last looked", regardless of which screen they last looked at.

## D8 — A dismissed push offer is remembered per device, and made again after 30 days (2026-08-11)

Conflict: [#167](https://github.com/drewdrewthis/playa-post/issues/167) says the notifications panel must stop offering push to a device that already has it, and must stop re-offering it to somebody who closed the browser's permission dialog without answering. Enrolment needs no decision — it is recoverable from the browser, because a held subscription is a fact `pushManager.getSubscription()` will state on request. A **dismissal** is not: the Push API records nothing when a person waves the prompt away, so "this one was asked and said not now" exists only if the app writes it down, and where it is written decides who it is true of.

Decision: **write it on the device, in `localStorage`, and make the offer again after 30 days.**

**Device-local, because push enrolment is itself a device fact.** A subscription lives in one browser's own service worker registration; the same person on a phone and a laptop is two enrolments or one, and the server cannot tell which — `app.push_subscriptions` is keyed on `owner_id`, one row per person, so it could not answer "is *this* device enrolled" even if asked. The answer "not on this device, thanks" is therefore a device answer too. An account-level record would suppress the offer on a new device where it has never been made, which is the opposite of the bug being fixed: a person who declined on a laptop in April would install the PWA on their phone in August and never be offered the notifications they came for.

**Two facts at most, and a device may never hold both.** The marker keeps the VAPID public key this device enrolled under (the key, not a boolean — a subscription is bound for life to the key that minted it, so after the rotation `docs/engineering/secrets.md` §4 prescribes, "subscribed" under the superseded key is not subscribed) and the time the prompt was last dismissed. Enrolling clears the dismissal, because the device has now answered yes to the question that recorded one.

**The marker is a hint for the first paint; the browser is the authority.** The panel reads enrolment twice — synchronously from the marker, so a device that enrolled last week paints "Push is on for this device." on the first frame instead of flashing consent copy at somebody who has already consented, and then again a tick later from the subscription the browser is actually holding, which corrects and reconciles it. Nothing is ever *believed* over the browser. That is what makes the storage safe to be wrong: it can only ever be wrong for one frame.

**A cooldown, not a retirement.** Dismissing a browser permission dialog is as often a stray tap or an Escape as a decision, and "clear this site's data" is not a path back anybody will find. Accepted consequence, in both directions: somebody who meant it is offered push again in a month, in a panel they only reach by choosing to look at their notifications; somebody who changes their mind either presses again before leaving the panel — the control is unchanged within the session, so a second press asks again — or waits up to 30 days. No settings screen is built for this, and none should be until something else needs one.

Corollaries, recorded so the model is deliberate rather than accidental:

- **A granted permission outranks a recorded dismissal.** The dismissal records "the browser asked and got no answer"; a permission that is now `granted` means the question has since been answered yes, in the browser's own settings. So the offer returns immediately in that case rather than waiting out the cooldown — it is the one quick way back for somebody who changed their mind, and honouring the dismissal there would leave them none.
- **A browser block is still named, ahead of the dismissal.** Chrome blocks an origin by itself after repeated dismissals, so "dismissed, then blocked" arrives without anybody choosing it. The panel says so, with the copy that names the browser settings as the only remedy, rather than going quiet and leaving a reader wondering why the app never mentions push.
- **Revoking permission un-enrols the device on the next load.** Permission is checked before the held subscription is even looked at, so neither the marker nor a subscription the browser has not got round to dropping can keep the enrolled line on screen. The stale marker is cleared as it goes, so the correction survives the reload rather than being re-made every time.
- **"Cannot see" is not "not enrolled".** With no service worker registered — a `pnpm dev` run, or the seconds a fresh install spends registering one — nothing is claimed and nothing is forgotten. A settled read that answered "not enrolled" there would clear a working device's marker on a race.
- **Unavailable storage costs a flash, never a failure.** A locked-down profile throws on `localStorage` access; every read and write is guarded, an unreadable marker reads as empty, and correctness is unaffected because the subscription is still the authority. That device pays one frame of consent copy per panel opening.

## D9 — The bulletin-removal action is called "Remove"; removed bulletins stay visible to their author (2026-08-11, owner-directed)

Conflict: [#168](https://github.com/drewdrewthis/playa-post/issues/168) — the owner asked that "Archive should be remove and can be soft deleted." The action already soft-deletes (`Bulletin.archivedAt`), so only the name was wrong; but renaming reopened whether a removed bulletin should keep appearing, marked, on its author's own board.

Decision: **rename the copy only; keep the current visibility semantics.** Every user-facing surface of this action now says "Remove"/"Removed" — the detail sheet's button, the card's pill, the offline sync queue's row label, and the report-own-bulletin refusal copy. The mechanism is unchanged: `archivedAt` soft delete, no hard delete, and a removed bulletin remains visible to its author, marked as removed, exactly as before. Any change to those semantics — including whether removal should eventually hide the bulletin from its author, and how long soft-deleted rows live — is deferred to [#169](https://github.com/drewdrewthis/playa-post/issues/169) (uniform soft delete + purge), which owns that model as a whole. ⚠ **[D17](#d17--every-delete-is-soft-and-every-soft-delete-expires-notes-are-excluded-because-they-have-no-delete-2026-08-12) is that answer**: `archived_at` is confirmed as the bulletin soft delete and keeps its name, and a removed bulletin now leaves its author's own list too — once it is older than `PURGE_RETENTION_DAYS`, because the row stops existing. Internal identifiers (`archivedAt`, `bulletins.archive`, `bulletin-archive-button`, `data-archived`) keep their names: they describe the mechanism, not the copy, and renaming them would churn the API contract and stored offline mutations for no user-visible gain.

## D10 — One rejected-code message, not two: GoTrue cannot tell wrong from expired from reused (2026-08-11)

Conflict: [#179](https://github.com/drewdrewthis/playa-post/issues/179)'s ACs ask for an incorrect code's failure state to be "distinct from an expired code," and separately for an expired code to tell the user to request a new one — two bullets that read as two different user-facing messages. Supabase's GoTrue answers a wrong digit, an expired code, and an already-spent code with the identical signal: HTTP 403, `error_code: otp_expired`. Verifying a code is one lookup against one stored token, and all three causes leave that lookup with nothing to find — there is no field on the wire, and no accompanying data, that says which of the three happened.

Decision: **one honest message, not two guessed ones.** `describeSignInFailure` maps `otp_expired` to a single string naming all three possible causes and the one remedy that fixes all of them: "That code did not match — it may be mistyped, expired, or already used. Request a new sign-in email and enter the fresh code." The alternative — inferring "expired" vs. "wrong" from, say, elapsed time since the code was requested — was considered and rejected: it is a client-side guess about server-side state (the actual OTP expiry window, clock skew, a resend that reset the window), it can only drift out of sync with the real expiry as either side changes independently, and a wrong guess is worse than no guess — it would tell someone their code was "wrong" when they had in fact typed the right one too late, sending them to retype a code that could never work rather than to request a new one. AC4's "distinct from an expired code" is satisfied at the level the ACs actually gate: this is its own named branch in `sign-in-failure.ts`, tested on its own, and never falls through to the generic refusal — it is distinct from a rate limit, from a misconfigured build, and from the generic catch-all. It is not distinct from AC5's expired-code case, because nothing this app can see is either.

Corollary: this also answers AC6 (a spent code cannot be reused) implicitly rather than with a dedicated user-facing state — a reused code fails through the exact same branch, with the exact same message, because to GoTrue it is the exact same shape of failure as an expired one. There is nothing further to build for AC6 beyond what the provider already enforces.

## D11 — Passing an intro on requires the via's own note; a decline carries none (2026-08-11, owner-directed)

Conflict: [#175](https://github.com/drewdrewthis/playa-post/issues/175) — the owner asked that a via who passes an introduction on must add something of their own: "you have to add your own message." Issue [#89](https://github.com/drewdrewthis/playa-post/issues/89) shipped `intros.decide` as a bare decision with no content on either branch, and the target saw exactly one note: the requester's. The directive reopens what a pass-on *is*, and with it three questions #89 never had to answer — whether the note is required or offered, who reads it, and what a decline does with the same field.

Decision: **required on `pass_on`, forbidden on `decline`, and the target reads both notes with both authors named.**

**Required, not offered, because a pass-on is a vouch rather than a forward.** The whole premise of the one-hop introduction is that meeting a stranger goes *through* somebody who knows you both — and an intro passed on with nothing added is that person's name attached to a shrug. Making the note optional would have produced exactly the state the feature exists to prevent: a target reading a stranger's ask, seeing a mutual connection's name beside it, and being unable to tell whether that person actually thought it was a good idea. The requirement is the difference between a relay and an endorsement.

**The target sees two notes, each under its own author's card**, and never one joined paragraph. `IntroInboxRow` carries `note` (the requester's) and `viaNote` (the via's) as separate fields for that reason: attributing a vouch to the person being vouched for is the one misreading this screen must not permit, and a client that received one string could not avoid it. The via's card is projected from `app.visible_people(via, 0, 1)` — their own self-projection — which is the same **consent inversion** the requester's card already rests on, extended one person: *choosing to pass an introduction on is choosing to be seen by the target as its via.* It has to be, now that the via has words of their own on the row; a signature that disappears when the via's connection to the target lapses would leave an unattributed vouch behind, which is worse than no vouch.

**A decline carries no note, and one sent with a decline is refused rather than dropped.** The requester is told only that it was not passed on — no reason, no re-ask control (D6's sibling rule, `INTRO_NOT_PASSED_ON_LINE`) — so text written on a decline has no reader at all. Accepting the field and discarding it silently would let its writer believe otherwise, which is why `decideIntroInput`'s decline branch is a `strictObject` — over tRPC the refusal is the wire's own plain `BAD_REQUEST`, no application code — and why the domain keeps `INTRO_DECLINE_CARRIES_NO_NOTE` as its own backstop code for callers that bypass the wire, rather than a second meaning for `INTRO_CONTENT_INVALID`.

**The enforcement is deliberately split between the database and the domain, and the halves say different things.** `app.intro_requests.via_note` carries `check (via_note is null or status = 'passed_on')` — an *implication*, not the biconditional `intro_requests_decided_at` uses beside it. "Only a passed-on request may carry a via note" is true forever; "every passed-on request carries one" is not, because rows passed on before this migration have none and migrations are forward-only. So the database states what is possible for all time, and `domain/intro-note.policy.ts`'s `validateViaNote` states what is required *now* — on every new pass-on. A plain biconditional CHECK would have refused to apply against the pre-feature rows; Postgres's `not valid` variant would have applied by skipping them, at the price of a schema permanently asserting a requirement the stored data does not meet, validated nowhere.

Corollaries, recorded so the model is deliberate rather than accidental:

- **The via cannot read their own note back, and neither can the requester.** It is on the target's inbox row and nowhere else — not on `intros.listOutbox`, not on the decide receipt, not in an outbox event payload. That is a stronger rule than the one the requester's note is held to rather than the same one twice: the via wrote those words *to* the target, *about* the requester, and showing them to the requester would turn a vouch into something the person being vouched for reads over the writer's shoulder. Nobody writes an honest one twice.
- **The bound is the requester's bound**, 1–4000 after trimming, from the same constant and the same policy file. Both notes land in `text` columns on one row and are read on one screen, so a via allowed more room than the person they are vouching for would be a rule nobody chose.
- **Absent and empty are one refusal.** A pass-on with no `note` field and one with `''` are the same fact about what the target would read, so both answer `INTRO_CONTENT_INVALID` rather than getting a code each. The wire schema's `min(1)` is about the union being honest — the branch that says "this one has a note" must not accept a request with none in it — and trimming stays the domain's, because that is where its refusal code lives.
- **Introductions passed on before this shipped keep working, unsigned.** Their rows carry `via_note = null`, the wire omits the key, and the client renders the requester's half alone. There is no placeholder: an empty quote attributed to somebody is worse than a note they never wrote.

## D12 — Accepting an introduction is a token-free mutation, and the connection is formed from a published event (2026-08-12)

Conflict: [#166](https://github.com/drewdrewthis/playa-post/issues/166) — a passed-on introduction had no answer. The target's row rendered read-only while the via's carried controls, and `modules/intros/domain/intro-request.ts` recorded that post-`passed_on` action was deliberately out of scope for [#89](https://github.com/drewdrewthis/playa-post/issues/89) because "minting a connection from an intro is a new authorization path". The issue left the mechanism explicitly unresolved: **mint a bearer invite token and reuse `connections.acceptInvite`, or add a token-free mutation.** Connections had exactly one way to form until now, and this makes a second, so the choice is a trust-model decision rather than an implementation detail.

Decision: **a token-free `intros.respond`, authorized by the caller's own resolved actor; the connection is written by `modules/connections` from an `IntroAccepted` outbox event.**

**Token-free, because a minted bearer token would be an unaddressed artifact solving a problem we do not have.** The caller's identity is already authenticated at the tRPC boundary and the row already names its target, so `where target_id = <actor> and status = 'passed_on'` is a complete authorization in one statement. A token, by contrast, arrives with a fourth set of questions nobody asked: where it is stored, how long it lives, what revokes it, what happens when it leaks, and what a second person holding it may do. `app.invitations` answers those for a *transferable* claim — an invite is meant to be handed to somebody unnamed, which is exactly why it is bearer-shaped. An introduction names all three parties at the moment it is written; making it transferable would let the one thing the one-hop design forbids happen, which is somebody outside the triangle acting on it.

**The consent inversion (ADR-0017 D4/D8) is preserved rather than stretched.** Every party has already consented in their own act by the time this mutation is reachable: the requester consented by asking (and was told, before send, that asking is consent to be seen), the via consented by passing it on with a note under their own name, and the target consents here by accepting. Nothing new is disclosed at acceptance — the target has already read both notes and both cards — so this adds a *write* to the model, not a disclosure.

**The connection is formed from an event, not from a call, and that is the load-bearing half.** `modules/intros` writes `status = 'accepted'` and `IntroAccepted` in one transaction; `modules/connections` subscribes to that event and writes the edge under its own `app.consumer_receipts` row. Two properties follow that a direct call cannot provide:

- **A crash cannot lose the connection.** A synchronous call would put the acceptance and the edge in two transactions, and a failure between them leaves an introduction that says `accepted` with no connection — unrecoverable, because answering is terminal-once and nobody may retry. With the outbox the failure mode is a delivery still owed, which is precisely what ADR-0006's retry and dead-letter path already handles.
- **`app.connections` keeps one writer.** Cross-module row creation is what addendum §19 forbids and `sql-table-ownership` polices; `modules/intros` never learns `modules/connections` exists, and the two modules' only coupling is the event *name*.

The price is honest and small: the edge lands on the drainer's next round rather than instantly, so the acceptance confirmation says "you are being connected" rather than claiming it is done, and the e2e polls a reloaded graph. A UI that promised an instantaneous connection would have been the version of this that lies.

**The target's answer needs its own vocabulary, in two places.** The status is `target_declined` rather than a second use of `declined`: that one says the via would not pass it on and the target was never told, this one says the target read it and said no, and collapsing them would silently widen every read that filters on the first. The timestamp is `responded_at` rather than a reused `decided_at`: they belong to two different people, the interval between them is the only record of how long an introduction sat unanswered, and `IntroAccepted.occurredAt` reads the target's — an acceptance stamped with the via's time would claim the target answered before they were shown anything.

Corollaries, recorded so the model is deliberate rather than accidental:

- **A target's decline is invisible to the requester, and indistinguishable from an introduction nobody has answered yet.** This is ADR-0017's founding invariant applied one person along: somebody who can be *seen* refusing cannot safely refuse, and an introduction is worth nothing if the person receiving it is under obligation. `intros.listOutbox` therefore reports the **via's** decision only — `accepted` and `target_declined` both read back there as `passed_on` — and carries no answer time. An acceptance still reaches the requester, because it discloses itself by connecting, which is the target's own act rather than the read's.
- **The same refusal answers every reason, including "the via declined it".** `INTRO_UNAVAILABLE` covers not-yours, already-answered, still-open and via-declined alike. A distinct refusal for the last one would let a target detect a decline simply by trying to accept it, reopening from the other side the exact oracle the feature closed.
- **Eligibility is deliberately not re-checked on the answer**, unlike a pass-on (ADR-0017 D3). A pass-on re-asks the graph because it is about to disclose the requester to somebody; an answer discloses nothing new, because the target has already read the introduction. Refusing it now would withdraw nothing and would strand somebody holding an introduction they can neither accept nor refuse.
- **An accepted introduction produces exactly the connection an accepted invite produces** — `accepted`, `full` both ways, from the columns' own defaults, and no trust row. An intro-formed connection that disclosed differently would be a second connection model nobody chose. `ConnectionAccepted` carries `introRequestId` where an invite-formed one carries `invitationId`, as one union rather than two event types: "these two are now connected" is one fact whoever caused it, and a second type would mean every future consumer had to remember to subscribe twice.
- **Introductions passed on before this shipped are answerable.** They carry `responded_at = null` and status `passed_on`, which is exactly the state the new mutation acts on. The two CHECKs that had to move did so for that reason: `intro_requests_status` widened to five values, and `intro_requests_via_note` — written when `passed_on` was terminal — would otherwise have refused the very UPDATE that accepts an introduction carrying a vouch.

## D13 — Dismiss is a board-bulletin action only; the intro inbox keeps its terminal decline (2026-08-11)

Conflict: [#170](https://github.com/drewdrewthis/playa-post/issues/170) — the owner asked that "when you dismiss something, it should go to a 'dismissed' category" and named no surface. Three could have taken the word: board bulletins, the notifications panel (which already had a dismissal of its own before this issue), and the intro inbox. AC6 asks for the choice to be recorded rather than assumed.

Decision: **board bulletins, and nothing else.** `moderation.dismiss` and `moderation.undismiss` are the two directions, `bulletins.dismissed` is the category behind them, and the category is a second view of the board rather than a screen of its own. The notifications panel keeps the dismissal it already had — a different mechanism under the same word, deliberately separate from "seen" (D7) and belonging to a notification rather than to the thing it is about. The intro inbox gains nothing.

**The intro inbox already has a terminal answer, and a second removal affordance there would be two overlapping states.** A passed-on introduction is answered once — accepted or declined, `responded_at` written once, a second answer refused ([#166](https://github.com/drewdrewthis/playa-post/issues/166), D12) — and a decline is invisible to the requester by design. Adding dismiss beside that gives every row two ways to leave the screen with no agreed meaning between them: whether a dismissed-but-unanswered introduction is still owed an answer, whether declining a dismissed one still reaches nobody, and what an un-dismissal of an answered row would even restore. None of those questions has a good answer, and none of them buys the target anything that declining does not already give them. An introduction is also a thing another person is waiting on, which a bulletin is not: hiding one without answering it is exactly the silence the one-hop design exists to prevent.

**Un-dismiss is online-only, and symmetric with dismiss.** Neither direction is queued for offline replay. `bulletin.dismiss` has no replay handler and `bulletin.undismiss` does not either; both are recognised mutation types server-side so that the type-agnostic actorship gate refuses an unrelated actor *before* dispatch discovers there is no handler, and the replay half arrives for both at once with [#63](https://github.com/drewdrewthis/playa-post/issues/63)'s sync grammar. The symmetry is the decision rather than an accident of what was built first: a control that worked with the radio off in one direction and not the other would teach a person a rule that is false half the time, which is worse than one that works in neither direction and says so.

Corollaries, recorded so the model is deliberate rather than accidental:

- **A note pinned to somebody's board carries no dismiss either.** The board interleaves two kinds of card and only one of them has this action. A note was addressed to its recipient and handed over (D6); the recipient's remedy for an unwanted one is the connection itself, not a per-note hide, and building one would be the first half of a moderation model for private messages that this product does not have.
- **A viewer may dismiss their own bulletin.** The visibility traversal seeds at the viewer, so an author's own post is visible to them and therefore dismissable by them — an author tired of seeing their own request is making a statement about their own board, which is precisely what this operation is. Reporting stays refused for one's own bulletin, because that one means "this is unwanted content" and removal is the author's tool for it. Consequence for every client: the Dismissed category holds rows the viewer wrote, so it must mark them as theirs rather than assuming a dismissal is always somebody else's post.
- **Dismissal publishes no event and remains invisible to everyone else.** It alters nothing about the bulletin — not `archivedAt`, not `version` — and an author cannot tell that it happened. A preference that emitted an outbox event would be a preference other people could observe.

## D14 — "Pin a note back" is a new note to the note's author, not an operation on the note (2026-08-11, owner-directed)

Conflict: [#176](https://github.com/drewdrewthis/playa-post/issues/176) — the owner asked that "you should be able to click on a note for an expanded view so you can pin a note back". Both halves land on a recorded decision that says no. `apps/web/src/app/notes/note-card.tsx` stated that "a tap would raise a sheet whose entire contents were already on the card, so the card is not a tap target", and `apps/server/src/modules/notes/transport/notes.router.ts` stated that there are "two procedures, and there is deliberately no third", naming `getById` as the one it was refusing. Worse, "pin a note **back**" has no referent at all in the model: `apps/server/src/modules/notes/domain/note.ts` gives a note no `version` and no `archivedAt`, decision D6 gave `app.notes` no unpin, no archive, no edit and no delete, and D13's own corollary reaffirmed that a note carries no dismiss either. There is nothing on a note that "back" could toggle. The ask therefore cannot be implemented until somebody says what it *means*, which is what this record does.

Decision: **pin-back is composing a new note addressed to the author of the one being read, through the existing `notes.pin` and its existing first-degree gate.** The expanded view is a read — a new `notes.getById` over the same `app.visible_notes` the list already composes — and the control it carries is a navigation into the compose screen that already exists, with the recipient preselected (`/board/new?noteTo=<authorId>`). No new table, no new column, no migration, no new mutation, and no lifecycle.

**Reply-by-note rather than a lifecycle, because a lifecycle is a much larger thing than the ask.** The alternative readings each require inventing state a note has never had: "un-pin it" needs a removal and therefore a moderation model for private messages this product does not have; "re-pin it to the top" needs an ordering column and turns a board into a feed somebody curates; "acknowledge it" needs a read receipt, which is exactly the delivery confirmation PDF §6 keeps out of a channel with no sent list. Answering, by contrast, needs nothing new: it is the gesture the product already has for reaching a person, aimed at the person who just reached you. It is also what the words most plainly describe — somebody left a note on your board, and you leave one on theirs.

**The read is a second caller, never a second rule.** `notes.getById` composes `app.visible_notes` and adds an id predicate over it, so a note it can return is a note `notes.list` would already have returned. Two reads of one authorized set cannot disagree about who may read what — which is the property that makes adding a read cheap here and would have made adding a second `where` over `app.notes` a §6 violation.

Corollaries, recorded so the model is deliberate rather than accidental:

- **The "card is not a tap target" decision is reversed, and the reasoning that supported it no longer holds.** That note argued a sheet would only repeat the card's own text. True, and beside the point once the sheet has something the card does not: the way to answer. The body stays on the card regardless — a note has no title to be a headline with — so this is the one card in this product whose expanded view is not about revealing more text.
- **The "no lifecycle" decision is revisited and deliberately kept.** Notes stay immutable and pin-only: no unpin, no archive, no edit, no version, no read state, no ordering column. Pin-back writes a second row and touches the first not at all, which is why #176 ships with no migration. `version` still arrives with the first mutation ADR-0005 marks `expectedVersion: yes`, and not before.
- **There is still no `listSent` and no receipt, and this read does not become one.** `app.visible_notes` gates on `recipient_id = viewer_id`, so an author asking for a note they pinned gets `NOTE_GONE` — byte-identical to what a stranger gets and to what a UUID naming no note gets. A read that answered the author differently would turn the private channel's only fetch into the delivery confirmation D6 denied it, so the author's refusal is asserted alongside the stranger's rather than left as a consequence nobody checked.
- **An author who has left the viewer's world gets no pin-back control at all — not a disabled one, and no explanation.** `app.visible_notes` LEFT-joins the authorized person set, so a delivered note outlives its author's departure and arrives with no author card and no `userId` whatsoever. There is literally nobody to address, and filling one in from the viewer's own graph or from the connection they remember is the §6a person-projection bug (ADR-0002 B5) on the surface where a reader is most likely to believe they already know the answer.
- **A present author card is necessary but not sufficient; the degree is read again at open time.** That set is the whole visible world, not just direct connections, so the author of a note may now be two or six hops away. Pinning required degree 1 *at the time* and the read never re-derives it, so the sheet asks the graph and offers the control only at degree 1 — a UX gate, never an authorization one, exactly as `note-reach.ts` already governs the bulletin sheet's version of the same control. The authorization stays inside `notes.pin`'s insert, which refuses an ineligible recipient identically to one who does not exist.
- **Past the first degree the note sheet states the distance and stops — no intro control.** The bulletin sheet offers one because reaching a stranger's author is its whole purpose; a note is already a message from somebody who was a direct connection, and answering it with "ask a third person to introduce you to the person who wrote to you" is a different feature ([#89](https://github.com/drewdrewthis/playa-post/issues/89)) on a surface that does not need it.
- **The offline story is unchanged, because pin-back is a pin.** It enters the same `sync.submitMutations` `note.pin` envelope, queues the same way online or off, and a recipient who has stopped being a direct connection by the time the queue drains is refused then, by the insert. The read is a read and is not queued at all.

## D15 — A display name is editable; a handle is not, and reopening that needs ADR-0008 amended first (2026-08-11)

Conflict: [#177](https://github.com/drewdrewthis/playa-post/issues/177) asks for editable display names and puts the handle in parentheses — "(and handle?)" — leaving the second half explicitly open. The two look like one feature and are not. `apps/server/src/modules/identity/domain/user.ts` records a display name as an ordinary column and a handle as "chosen at onboarding and immutable in v1 (rule 4)", and [ADR-0008](../adr/ADR-0008-identity-model.md) gives that immutability an anti-impersonation rationale rather than a convenience one.

Decision: **the display name becomes editable; the handle does not, and this issue does not amend ADR-0008.**

**Handle editing is deferred, and [ADR-0008](../adr/ADR-0008-identity-model.md) rule 4 is the blocker.** Re-issuing a retired handle lets its next holder inherit shared links, printed cards, and real-world recognition — in a network whose whole premise is recognition, that is an impersonation vector, not an inconvenience. The ADR already names the mitigation a change would need (tombstoning the old handle, and an operator-assisted support path rather than a self-serve one), which is the shape of the work somebody reopening this would have to do first. AC3 asked for the choice to be recorded rather than assumed; this is that record. Anyone who wants handle editing amends ADR-0008 and comes back — a rule with a stated rationale is not overturned by an implementation PR.

**The refusal is audible rather than silent.** `identity.updateDisplayName`'s input is a `strictObject`, so a client sending `handle` alongside the name is rejected instead of having the field quietly stripped. This is `decide-intro.input.ts`'s reasoning (D11) applied to a stricter field: accepting something and discarding it lets its sender believe otherwise, and the belief here is "I have changed my handle". The same strictness refuses a supplied `userId`/`viewerId`/`actorId`/`ownerId` outright, which is the loudest available answer to somebody probing whether the procedure can be aimed at another person.

**The bounds are onboarding's, shared rather than restated.** `modules/identity/transport/display-name.ts` holds one schema — trimmed, at least one character, at most 80 — and both `identity.completeOnboarding` and `identity.updateDisplayName` take it. Two copies would be two rules the day somebody changed one, and the failure is silent in the worst direction: a name a person could choose at sign-up but not restore afterwards, or the reverse. The bound stays a *transport* concern, as `complete-onboarding.input.ts` already recorded — `app.users.display_name` is bare `text`, nothing in ADR-0008 constrains it, and "how big may a request field be" is a question about the wire. No migration, therefore: the column already accepts everything this rule allows.

**No outbox event, and the reason is stronger than the precedent.** The sibling `identity.visibility.set` publishes none either, but the argument here does not rest on that. Every rendering of a person's name is projected from `app.users.display_name` at read time through `app.visible_people`'s disclosure gate (ADR-0002 §6a), so **there is no derived copy anywhere for an event to go and correct** — the next read is already right, which is how AC5 is satisfied without any cache-invalidation machinery. Publishing one would also contradict a rule this module already enforces: `UserOnboarded` deliberately carries `userId` and `handle` only, because "a display name is personal data and an outbox row is a durable, widely-read log". An event whose entire payload was the new name would durably record every name a person has ever gone by, which is precisely the hazard that comment refuses.

Corollaries, recorded so the model is deliberate rather than accidental:

- **`identity.updateDisplayName`, and there is no matching read.** A person's own name already arrives on `graph.list` — they sit on their own graph at degree 0 with `full` disclosure — so a `displayName.get` would be a second answer to a question already answered, and two answers eventually disagree. That is also why this is a bare mutation rather than an `identity.displayName.*` namespace like the visibility dial: a one-procedure namespace is a placeholder for a sibling that must not exist (addendum §4).
- **The row's `version` is not bumped.** ADR-0005's per-mutation matrix has no row for a rename, and `setVisibleToDistance` set the precedent beside it: optimistic concurrency guards *content* two people can both edit, and this column has a single writer who is its owner. A conflict error here would read as "your own name change was rejected because your other device also changed it".
- **A rename is online-only and enters no offline queue.** It is not a `sync.submitMutations` envelope type, matching every other identity operation. Nothing about a name is worth queueing across a radio outage the way a bulletin is, and adding a mutation type is ADR-0005 grammar work with its own idempotency question.
- **Nothing new renders a name.** The client invalidates its whole query cache after a successful rename — `onboarding.tsx` already does this for exactly this field — and every screen then re-reads a §6a-gated projection. No new place derives a name from the graph, which is the constraint ADR-0002 §6a puts on any feature that touches this column: a viewer who was being told nothing about somebody is still told nothing after that person renames themselves.
- **Past names are not retained.** There is no history table and no audit row. Keeping one would be a durable record of who somebody used to be, which is the same personal-data hazard the outbox decision above turns down, arrived at from the other direction.

## D16 — Notify Me is a set, capped at six; D1's single-query rule is reopened (2026-08-12, owner-directed)

Conflict: **D1 is the decision being reopened.** D1 read PDF §4's "one special saved query called Notify Me" against the prototype's bell-on-every-card and resolved it in the PDF's favour — exactly one Notify Me query per user, with the per-view bell demoted to a *designation* of which view's query that was. The owner has since asked for the prototype's plain reading ([#172](https://github.com/drewdrewthis/playa-post/issues/172)): "you should be able to enable multiple notifications at once."

Decision: **the owner wins on the count; D1's structural half survives intact, and the bound D1 was carrying gets an explicit replacement.**

**`app.notify_me_queries` is still the sole answer to "who gets notified", and `app.saved_views` still carries no notify flag.** That was ADR-0016 D1's real content and it never depended on the number: a boolean on the view row would make the question answerable from two tables that could disagree, and `EvaluateNotifyMeHandler` would have to read both and reconcile them. What changes is the *key*. The primary key on `owner_id` — "D1 expressed as a database constraint rather than a convention" (ADR-0007:79) — becomes a surrogate `id`, and the invariant that replaces it is `UNIQUE NULLS NOT DISTINCT (owner_id, source_view_id)`: **one query per (owner, saved view), plus one untied query per owner.** The bell is still a designation and still enforced by a constraint rather than by application code; it is now a constraint over a set. Migration `20260812120000_notify_me_queries_per_view.sql` is data-preserving by construction — one row per owner is a subset of one row per (owner, view) — so an existing user's lit bell is still lit afterwards, with its query, its version and its designation untouched.

**`NULLS NOT DISTINCT` is load-bearing, not a flourish.** `views.notifyMe.update` names no row: the actor is the address, which under D1 worked because there was one row. It now means "your query that belongs to no view", and PostgreSQL's default — every `NULL` distinct — would let a person accumulate untied queries none of which that procedure could ever name again. The consequence, recorded because it is a real behaviour change: **`views.notifyMe.update` no longer takes the query away from a lit bell.** Under D1 writing one query necessarily detached it from whichever view it came from; the two are now separate rows and neither write path can reach the other's. An `expectedVersion` naming a designated query's version is a conflict rather than a rewrite, which is the honest answer — that row is not the one this procedure addresses.

**The cap is six, and it is not the saved-view cap.** AC4 asked whether a cap replaces the read-cost bound D1's primary key was providing, and it has to: `EvaluateNotifyMeHandler` runs one authorized read per switched-on query on **every** `BulletinCreated`, so the number of queries per person is a multiplier on background work that every other person's posting pays for. Reusing `SAVED_VIEW_LIMIT_PER_OWNER` (24, ADR-0016 D3) was the obvious move and is wrong, because the two caps have different payers: 24 bounds a *per-render* fan-out somebody creates on a screen they chose to open and pays for themselves, and letting it double as the background cap would set a number chosen against one cost loose against a cost it was never weighed against. Six is above any plausible curated set of alerts and holds the worst case to a small constant multiple of what D1 allowed.

**Precisely: six *designated* queries, plus at most one untied query, so at most seven rows per person.** The two halves are bounded by different things and deliberately so. The bells are bounded by the cap, which counts only rows with a `source_view_id`; the untied query is bounded at one by `UNIQUE NULLS NOT DISTINCT` and is not counted at all. A single count over all of an owner's rows — the first cut — reads as simpler and is wrong twice over: it silently spends a bell slot on a query that sits on no card, so a person holding an untied query gets five bells rather than six, and the refusal it produces says "switch one off" while pointing at cards none of which could free the slot. There is correspondingly **no cap on `views.notifyMe.update`**: the key already holds that row at one, so a count there would bound nothing, and somebody with every bell lit can still save the query they came to save. The evaluator's bound is unaffected — seven is a small constant, which is the whole of what the cap was for. Like the saved-view cap it is **soft** — counted inside the write's transaction, unlocked, so a race can land one extra row, the same trade `SAVED_VIEW_LIMIT_PER_OWNER` already makes — and raisable as a one-constant change with no migration, because the schema enforces uniqueness and never a count.

Corollaries, recorded so the model is deliberate rather than accidental:

- **A person is matched at most once per bulletin, however many of their queries match.** Before D16 "one row per matching query" and "one row per matching person" were the same sentence; they are not any more, and the difference is user-visible — a `NotifyMeMatched` per query would put one bulletin into somebody's grouping window several times and push it at them once per bell. `EvaluateNotifyMeHandler` settles a person at their first match, which also means a person whose bulletins match costs one read and only a person nothing matches pays for all of theirs. That is the case the cap bounds.
- **The aggregate is the query, not the person.** `NotifyMeQueryChanged` and `NotifyMeQueryCleared` route on the new `id` and carry it; routing on `owner_id` would leave a consumer told "something about your notifications changed" with no way to order or act on it, and a `Cleared` naming only the owner would say "stop sending" about bells that are still on. Payloads are unchanged otherwise: identifiers and routing data, never the query text (ADR-0006, M2-AC16).
- **Which bell produced a match is not something a notification says.** The evaluator's read model deliberately does not select `source_view_id`. A notification is about a bulletin, and carrying a saved view's identity into the fan-out path would put it there for nobody to read.
- **Switching a bell on can now be refused, which D1 made impossible.** The Saved screen reports that refusal in the server's own words — it names the bound and echoes none of the person's input — rather than as "check your connection", which is advice somebody at the cap will act on forever with no effect.
- **`ON DELETE` is still absent and deleting a view still stops that view's notifications only.** Every statement touching `app.notify_me_queries` from the saved-view side carries both `owner_id` and `source_view_id`; under D1 the second predicate was defence in depth against a single row, and it is now the whole of AC2.
- **No per-query preferences, no per-query naming, and no way to see which bell fired.** A notification is still one grouped push about bulletins. Those are M5's preferences work if they are ever wanted, and inventing them here would be building a surface nothing has asked for.

## D17 — Every delete is soft and every soft delete expires; notes are excluded because they have no delete (2026-08-12)

Conflict: [#169](https://github.com/drewdrewthis/playa-post/issues/169) asks for one uniform delete model across "bulletins, saved views, any future deletable entity", and the three deletable-looking things in this product disagreed with each other. `app.bulletins` soft-deleted via `archived_at` and kept the row forever. `app.saved_views` hard-deleted. `app.notes` had no delete at all. [D9](#d9--the-bulletin-removal-action-is-called-remove-removed-bulletins-stay-visible-to-their-author-2026-08-11-owner-directed) had already deferred "how long soft-deleted rows live" to this issue, and [#118](https://github.com/drewdrewthis/playa-post/issues/118) had already named the missing purge as a gap.

Decision: **soft delete becomes the shape of every user-facing delete that exists, a configurable purge makes it finite, and notes are explicitly excluded rather than quietly forgotten.**

**`archived_at` IS the bulletin soft delete, and this issue adds nothing to that table.** Naming it uniformly was the first temptation and it is wrong twice over: D9 already refused to rename `archivedAt`, `bulletin.archive`, and the stored offline-mutation type, because those describe the mechanism rather than the copy and renaming them churns the API contract for no user-visible gain; and a second `deleted_at` beside `archived_at` would be two representations of one fact, where the second one written is the one some read believed. The two columns therefore stay spelled differently and mean the same thing, which is recorded here rather than left for the next reader to rediscover.

**Saved views are the half that changes.** `app.saved_views` gains `deleted_at`, `views.saved.delete` becomes an `UPDATE`, and every read of that table carries `deleted_at is null`. Nothing above the repository can tell: the view leaves the list, its name is free immediately, its cap slot is free immediately, it cannot be renamed back into existence by a client holding a stale list, and its bell cannot be re-lit — refused byte-identically to a view id that names nothing (M5-AC16). The second delete still answers `deleted: false` without moving the original stamp, so idempotency and the anti-oracle silence both survive the change of mechanism.

**The one thing that is NOT soft is the Notify Me designation.** Deleting a view still deletes its `app.notify_me_queries` row outright, in the same transaction, and still emits `NotifyMeQueryCleared`. A designation is not content of somebody's to keep recoverable — it is a live instruction to push notifications at them, and a row stamped `deleted_at` on a table nothing filters would keep sending, with its only off-switch on a card that no longer exists. Worth stating because the constraint that used to force the ordering has stopped forcing it: a soft-deleted view row still satisfies `notify_me_queries_source_view_fkey`, so what was defence in depth backed by the database is now one predicate in one file, and the purge carries a backstop that stops a future edit from wedging the sweep instead of announcing itself.

**Notes are excluded, and the exclusion is the decision rather than an omission.** `app.notes` has no delete, no unpin, no archive, no edit, no read state — [D6](#d6--private-notes-are-back-as-a-separate-module-and-never-a-bulletin-type-2026-08-10-owner-directed) made notes immutable and pin-only, and [D14](#d14--pin-a-note-back-is-a-new-note-to-the-notes-author-not-an-operation-on-the-note-2026-08-11-owner-directed) revisited that and deliberately kept it ("no unpin, no archive, no edit, no version, no read state, no ordering column"). #169 asks for soft delete on *user-facing delete actions*, and there is none here to make soft. Adding `deleted_at` anyway would be a column no mutation ever sets — precisely the trap `create_notification_dismissals.sql` names, where every later reader has to guess what the absence of a writer means. **If a note delete ever ships it arrives with `deleted_at` from day one and a purge target in the same commit**; that is the standing requirement this entry exists to leave behind. The purge suite asserts the sweep leaves notes alone, so "we did not build that" is recorded positively rather than inferred from silence.

**The window is configuration, the cadence is not.** `PURGE_RETENTION_DAYS` defaults to 30 and is bounded at 1. A default is safe here on the environment schema's own terms — a retention window names no external system, so there is no wrong-but-plausible value that could point a deployment at somebody else's data — and the lower bound is the safety property: zero or negative would purge a row the moment somebody deleted it, which is a hard delete wearing a sweep's name and would be invisible, because every read already hides the row. How *often* the sweep runs is an hourly constant in `entrypoints/purge/start-purge-poller.ts` and deliberately not configurable: an operator has a policy about how long deleted data lives and no opinion about poll intervals, and an hour is three orders of magnitude below the shortest legal window, so every setting of that second knob would produce the same observable retention.

Corollaries, recorded so the model is deliberate rather than accidental:

- **The purge covers user-deleted state only, and expiry is not deletion.** A bulletin whose `expires_at` has passed is off every board and still its author's; sweeping on it would delete content nobody asked to be rid of. Whether an expired bulletin should eventually be archived on its own is a separate question and stays [#118](https://github.com/drewdrewthis/playa-post/issues/118)'s.
- **ADR-0006's own retention chores are not folded in.** Pruning `published` outbox rows at fourteen days and `app.mutation_results` daily are still unimplemented and still [#118](https://github.com/drewdrewthis/playa-post/issues/118)'s scope. They are a debugging-retention policy about infrastructure rather than a promise to a person about their own data, and putting two unrelated windows behind one configuration key would make the shorter one impossible to state. The poller is the obvious future home; each arrives as another target and its own window.
- **The purge publishes nothing.** No outbox event from the sweep or either store. The state change was the delete, thirty days earlier, and it published whatever it owed then. An event here would tell a consumer "this was deleted" about something already absent from every read for a month, and would durably record that a person deleted something long after the fact — the hazard `UserOnboarded`'s payload rule and M2-AC16 both refuse from other directions. What is recorded is a count, in a log line carrying no row, author, or owner identifier, and only for rounds that actually removed something.
- **A purged bulletin takes its reports and dismissals with it, by cascade, and that is the first `ON DELETE` clause in this schema.** `create_saved_views.sql` states the rule being excepted: no cascades, because deleting a notifying view must *stop the notifications*, a user-visible act a cascade would perform silently. A report and a dismissal are not like that — each is a fact about one bulletin with no meaning once it is gone, no user-visible consequence, and no consumer. What they do have is a `NOT NULL` foreign key that would refuse the purge permanently and quietly. The alternative was a statement in `modules/bulletins` naming `modules/moderation`'s tables, which is the cross-module reach-in addendum §19 forbids; expressed as a constraint, "a report cannot outlive its bulletin" binds every future deleter rather than whichever sweep remembered.
- **Moderation history for a removed bulletin therefore ends with the bulletin.** Somebody can post something reportable, remove it, and see the report cascade away thirty days later. That follows from the owner's own ask — this is what purging user-deleted content *means* — and the operator console it would matter to is M5 and does not exist. Anyone building it owes a decision about whether moderation evidence outlives the content it is about, and that is a retention policy of its own rather than a change to this one. `app.audit_entries` is untouched by the sweep either way.
- **A removed bulletin stops being visible to its author too, eventually.** D9 kept a removed bulletin on its author's own `bulletins.listMine`, marked. That is unchanged for the retention window and then ends, because the row stops existing. This is the only user-visible consequence of #169 on a surface that already worked, and it is the intended one: "removed" that never finishes is the thing being fixed.
- **Switching a flag off is not a delete, and stays hard.** "Every user-facing delete is soft" is a claim about somebody's *content*, and three user actions in this product delete a row without being that: `moderation.undismiss` removes an `app.bulletin_dismissals` row so a bulletin comes back to a board, and `views.notifyMe.update(false)` and `views.saved.delete` both remove an `app.notify_me_queries` row so a bell stops ringing. Each of those rows exists to say "this flag is currently on"; its absence is what "off" *is*. Soft-deleting one would leave the flag half-on — the row still there, still meaning on to every read that did not learn a new predicate, and the person who switched it off still hidden from a bulletin or still receiving pushes. There is also nothing to recover: the undo is the original action, available immediately and for free, which is the test that separates this category from a delete. The rule generalises — **a row whose presence encodes a live boolean is deleted outright; a row that is a person's own content is stamped** — and any future toggle stored as a row belongs on the first side of it.
- **A dependent row's fate follows who owns its table.** Two mechanisms in this entry look interchangeable and are not, so the default is stated rather than re-argued each time: **cascade when the dependent lives in another module and its disappearance has no user-visible consequence** — the constraint then binds every future deleter, and expressing it any other way requires a statement that reaches across a module boundary (§19); **write an explicit statement in the same transaction when the table is your own module's, or when its removal is something a person would notice** — the designation clear is that case, because it must also emit `NotifyMeQueryCleared`, and a cascade would have performed a user-visible act silently.
- **There is no undelete, and this does not build toward one.** The row surviving is what makes a purge possible and what makes an operator-assisted recovery *conceivable*; it is not a feature. No procedure, no API, no UI reads a soft-deleted row, and the two stores' reads are written so none can.

## D18 — A connection link is a permanent address, not a single-use key; the owner answers each request, and rotation replaces revocation (2026-08-12, owner-directed)

Conflict: [#206](https://github.com/drewdrewthis/playa-post/issues/206) reports that the invite link does the wrong thing three ways, and the three compound. `app.invitations` stores a **bearer credential**: holding the token *is* the consent, so opening `/i/:token` connects you outright, and the link is single-use, so it is spent by whoever opens it first. Every real use of a connect link is a *published address* — a QR on a camp sign, a URL in a bio, a link read out at a gathering — and against all three the invite model answers one person and refuses everybody after. The owner's workaround was minting a fresh token per person, which is the feature not existing. Nothing in the PDF settles it: §4 promises there is no people search, which is an argument for an opaque address and silent about how many people may use one.

Decision: **the link becomes a permanent, infinitely reusable address that names its owner and connects nobody; the owner accepts or declines each request; rotation is the only revocation; and abuse is bounded by limits rather than by the link running out.**

**A link is an address, not a key, and that single sentence produces everything else.** `/c/:slug` resolves to "here is who this is, and here is a button that asks them" — one read, no mutation, and no state anywhere that a tap could spend. Because holding the URL now grants *nothing*, publishing it is safe, so it can be permanent; because it is permanent, it is worth rotating; and because consent has moved to the owner, a forwarded link is no longer a connection with somebody they never chose. The obvious cheaper repair — make the existing token multi-use — fixes reuse and makes consent strictly worse: a standing bearer credential lets anybody who ever saw the URL connect at will, forever.

**The owner is the gate, and this is the same shape as an intro request one relationship along.** Opening somebody's link and pressing the button produces a request they answer; the connection exists only after they accept. [D12](#d12--accepting-an-introduction-is-a-token-free-mutation-and-the-connection-is-formed-from-a-published-event-2026-08-12) put mutual consent at the end of an introduction and this puts it at the end of a link, so every connection surface the product still points people at now tells one story about how two people become connected: somebody asks, and the other person says yes. (The one exception is deliberate and shrinking: a legacy `/i/:token` invite already sitting in somebody's chat history still connects its holder outright — see "Old invite links keep working, unchanged" below.) What the opener sees before they press is a sentence saying so, because somebody arriving from a QR expects a tap to connect them — that is what the link this replaces did, and the mismatch is what #206 was filed for.

**Rotation replaces revocation, it is silent, and it is destructive.** A single-use token has nothing to revoke after it works and nothing worth revoking before; a permanent address has the opposite problem, so the owner gets a one-tap rotation that mints a new slug. The retired slug is then stored **nowhere** — not in a `revoked_at` row, not in a `previous_slug` column — so the old URL answers exactly what an invented one answers, and it does so *by construction* rather than because some future query remembered a filter. The old URL says nothing about having been rotated, which is the point: the person most likely to still be holding it is frequently the reason it was rotated, and "this link was rotated" is a notification to exactly the person you rotated away from. The cost is stated rather than softened — one tap and the previous address is dead on every printed sign, every bio, and every chat message it was pasted into, with no undo, because there is nothing kept to undo it from. **Rotating touches nothing else**: connections stand, and requests already received are still answerable.

**Abuse is bounded by limits, not by use counts, and no limit is ever named to the person who hit it.** A request expires after fourteen days, an owner holds at most 32 pending requests at once, and one link produces at most 12 requests an hour. The rejected alternative was an "N uses" link, which reads like a compromise and is not one: the remaining count is invisible state the owner has to reason about, a spent link is indistinguishable from a rotated link and from a bug, and — decisively — it keeps the auto-connect-for-holder model this whole decision exists to retire. The limits are stated here as product facts because they are the ones a person can feel, and they are deliberately not *shown*: a full inbox and a rate-limited link answer the same neutral "not available" an unknown slug answers, since "not accepting requests right now" tells anybody holding a public URL how busy its owner is and tells a flooder where the ceiling is.

Corollaries, recorded so the model is deliberate rather than accidental:

- **A decline reaches nobody, and there is no "requests you sent" screen.** A requester learns of an acceptance the way an introduced pair does — the connection appears on their graph — and learns nothing at all of a refusal, which stays indistinguishable from a request nobody has got to yet. This is [D11](#d11--passing-an-intro-on-requires-the-vias-own-note-a-decline-carries-none-2026-08-11-owner-directed)'s invariant restated: an owner who cannot silently refuse will accept to avoid a confrontation, and then the gate is not a gate. The cost is real and is the intended trade — somebody refused waits on an answer that will never visibly come.
- **A request carries no message.** An intro request carries a note because the requester is asking a *third party* to vouch and a vouch needs words. Here the reader is the person themselves and the question is only "do I know this person", so a free-text field would be an unsolicited channel to a stranger — the exact thing the connection gate exists to require consent for. The owner sees a name and two buttons.
- **A declined pair may ask again immediately, and no cooldown ships with #206.** Same known vector [D11](#d11--passing-an-intro-on-requires-the-vias-own-note-a-decline-carries-none-2026-08-11-owner-directed) recorded, same reasoning: a cooldown is a decision about *how long*, which is this log's business and not a gap in the schema. The hourly rate limit is what stops it being a loop in the meantime.
- **Expiry is evaluated, never stored, so nothing can fall behind.** A fourteen-day-old request is simply gone to every read and to the owner's own Accept button; there is no `expired` state and no job maintaining one. A job that lagged would mean an owner accepting a request the rules say has already gone, which manufactures a connection out of consent that expired.
- **Old invite links keep working, unchanged.** `/i/:token` behaves exactly as it did, including its refusals, so a link already sitting in somebody's chat history still connects them. The two models coexist; retiring the older one is a separate decision with its own migration story, and #206 did not ask for it. What changes today is that the **You** screen offers the personal link instead of minting a token.
- **A stranger opening your link learns your name.** That is the feature — a screen that named nobody would not be an introduction to anything — and it is the same consent inversion [D12](#d12--accepting-an-introduction-is-a-token-free-mutation-and-the-connection-is-formed-from-a-published-event-2026-08-12) already accepted for intro targets: publishing your link *is* consent to be named to whoever opens it. It is bounded to that one screen, it discloses nothing else, and it stops the moment the link is rotated or the account is deactivated. Anyone whose answer to "may a stranger holding my URL see my name" is no should not publish the URL.
